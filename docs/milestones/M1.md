## Verified

- Sandbox flags, checked in a real container (PR #4): user 65532 when run as root, no capabilities, target and root filesystem read-only, output writable, network blocked, host environment hidden. The timeout removes the container, and the output cap works.
- Planted issues found in real runs (PRs #5, #6 and #8): gitleaks `github-pat`, checkov `CKV_DOCKER_8` and trivy `CVE-2019-14234` in `django==2.2.0`. The backend-rules check found the open Firestore rule and the Supabase table without RLS.
- bandit `B602` and gosec `G401`/`G501`, verified in CI only (PR #7).
- Real terminal run of the consent prompt (PR #11): it asked, showed a 24 MiB download, pulled and ran the image. The next run said "Already installed".
- Reports (PR #3, re-check): no scripts or external resources, strict CSP, all tool output escaped, files written with mode 0600, no "secure" or "passed" wording, and secrets masked.
- Recorded tool output from the pinned versions matches golden files (`TestRecordedToolOutput`).
- The code builds with Go 1.26.0, the minimum in go.mod (re-check).

## Unverified

- Rootless Docker, Podman and macOS Docker Desktop. CI runs the container tests only with rootful Docker on Ubuntu; the rootless warning waits for these tests (M2 follow-up).
- Whether gosec's results are complete for Go modules whose dependencies cannot be downloaded offline (PR #7). The gate only shows that it runs.
- govulncheck has not been run from the development machine (vuln.go.dev is blocked there). It runs in CI.
- The bandit and gosec images cannot be pulled on the development machine. They are verified only in CI.

## Known gaps

- Update containers can reach the local network until they are restricted through the egress proxy (ADR 0014, threat model T19; an approved M2 follow-up).
- Updates cannot go through an HTTP proxy or a TLS-intercepting network, and downloaded tool data is not pinned (ADR 0014).
- `backend-rules` does not recognize RLS enabled indirectly, for example inside a function, and reports such tables (ADR 0015).
- Issues that the 2026-11-19 re-check found in M1 work were fixed in M2-period PRs #20, #21 and #23 (see [M2.md](M2.md)).
