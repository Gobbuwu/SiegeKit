# 0024. Pinned file downloads

- Status: Accepted
- Date: 2026-11-19
- Amends: [0004](0004-plugin-manifest.md) (archive and binary artifacts get `size` and `mount`), [0008](0008-supply-chain.md) (where pinned files may come from), [0016](0016-dependency-consent.md) (a fourth kind of dependency)
- Amended by: [0027](0027-ffuf.md) (a wordlist ships inside SiegeKit)

## Context

M2.5 adds ffuf and Nuclei, and M2.9 adds Opengrep. Their publishers ship them as files on GitHub releases (a static binary in a `.tar.gz` or `.zip`), not as official container images, and some need data files of their own, such as a wordlist or a set of templates. Until now a plugin could only run a pinned image.

The owner decided on 2026-11-19 (M2.5 design, questions 1 and 2) that SiegeKit downloads such files itself, pinned by SHA-256, only from the publisher's GitHub releases and only with the user's consent, and that a static binary runs inside a pinned official image (for ffuf, the Alpine image the relay already uses) rather than in an image SiegeKit builds.

## Decision

1. **Manifest.** An artifact of kind `archive` or `binary` needs:
   - `ref`: an `https://github.com/` URL with no query, fragment or user name; an archive's URL ends in `.tar.gz`, `.tgz` or `.zip`;
   - `sha256` and `size`, the exact download size in bytes (at most 1 GiB);
   - `mount`: a path `/siegekit/files/NAME`, distinct for each platform.
   A plugin with such files must also have an `oci-image` to run in. The files used are those for `linux/<arch>` or `any`, because containers run Linux.
2. **Download.** SiegeKit downloads the file in its own process, never in a container that can see the user's files:
   - over HTTPS only, to `github.com` and the hosts GitHub sends release and source downloads to (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`, `codeload.github.com`), on port 443, following at most 5 redirects, and each redirect is checked against the same list;
   - through the HTTP proxy set in the environment, if any;
   - reading at most `size` + 1 bytes. The size and the SHA-256 must both match the pin before anything is unpacked.
3. **Unpacking.**
   - An archive may contain regular files and directories only: no links, devices or other types, no absolute paths, no `..` and no backslash tricks. It may unpack to at most 2 GiB and 200,000 entries.
   - Files are created new (never over an existing file), with mode `0755` if the archive marks them executable, otherwise `0644`, never setuid.
   - A `binary` becomes one executable file named after the URL's last path element.
4. **Storage.** Files live in `~/.local/share/siegekit/files/<sha256>/` (or under `$XDG_DATA_HOME`). The archive is unpacked into a temporary directory, moved into place, and only then is the marker `<sha256>.ok` written. A file counts as installed when both exist. The `files` directory is mode `0700`. Each unpacked directory is `0755`, so the tool's non-root user in the container can read it. A failed download leaves nothing behind.
5. **Consent (ADR 0016).** Each missing file is one more dependency in the question before the scan, with its exact size from the manifest and the tests that need it. A file several plugins share is listed and downloaded once. Declining it skips those tests. `--yes`, `--no-install` and `siegekit update` work as for images.
6. **Running.** Each file directory is mounted read-only at its `mount`. Everything else about the sandbox is unchanged (ADR 0006, 0019). If a file is missing at run time, the test fails with the file's name; it is never fetched during a scan.

## Consequences

- SiegeKit itself now makes outbound requests, but only to the GitHub hosts above and only after consent.
- A wrong or changed file never runs. A publisher replacing a release asset, or GitHub changing the bytes of a generated source archive, makes the download fail with a checksum error until the pin is updated in a reviewed pull request. Source archives (`/archive/refs/tags/...`) are generated by GitHub on request, so their bytes may change. Release assets uploaded by the publisher are preferred. Whether a given source archive stays stable is checked when a plugin first pins one (Nuclei templates, M2.5b).
- Files are checked once, when downloaded. Afterwards they are trusted like the image cache and tool data: they sit in the user's own `0700` data directory.
- Upgrading a pin leaves the old version's directory behind. Removing dependencies comes with the GUI Dependencies tab (ADR 0016) or a later command.
- Upstream signatures are not checked yet: checksum pinning is the guard, as for images. Signature checks are a planned follow-up (m2-plan, ADR 0008), after checking which publishers sign their files.

## Alternatives considered

- SiegeKit building its own images with these tools inside: SiegeKit would then publish and maintain third-party software, and users would trust SiegeKit's build instead of the publisher's release. Rejected by the owner (question 2).
- Downloading inside the tool's container: that container would need network access while it holds the user's code or reaches the target. Rejected (ADR 0006, 0014).
- Using a copy of the tool already on the user's machine: not pinned and not sandboxed. Rejected in ADR 0016.
