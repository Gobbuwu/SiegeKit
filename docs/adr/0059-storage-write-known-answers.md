# 0059. Known answers for the storage write test on the Firebase emulator and local Supabase Storage

- Status: Accepted (ADR 0058 item 9, from the design's build plan approved by the owner on 2026-11-21; item 6's fixture names: the owner chose the rename on 2026-11-23, on the condition that bandit, gosec and trivy are confirmed on this PR's CI before merge)
- Date: 2026-11-23
- Amends: [0058](0058-storage-write-test.md) (item 9: this is its PR 2)

## Context

ADR 0058 measured the storage write test by hand: the Firebase Storage emulator with rule sets v1 to v7 and Supabase storage-api with policy sets s1 to s7, on Docker and rootless Podman, cgroup v1 and (in a temporary job, removed before merge) cgroup v2. Nothing in CI runs the check against a real storage, so a change that stops it finding an open bucket, or that leaves a test file behind without naming it, would pass CI. Unit tests use a fake server that answers as measured, which cannot catch a change in how the real emulator or storage-api answers either.

## Decision

1. **A gate job `storage`**, matrix backend (`firebase`, `supabase`) × engine (`podman`, `docker`), 4 jobs. The storage runs in a container on the matrix's engine; SiegeKit's check runs in its own process, as in the other gate jobs since ADR 0054. It runs on every pull request the gate already runs on (code, `.github/gate/**`, known answers).
2. **Fixtures in `.github/gate/storage/`**: the 7 rule sets (`firebase/v1.rules` … `v7.rules`) and 7 policy sets (`supabase/s1.sql` … `s7.sql`) of ADR 0058's measurements, unchanged; the two small apps (`app/fb.js`, `app/sb.js`), bundled in the job with esbuild `--minify` from the firebase 12.19.0 and supabase-js 2.49.4 SDKs; the `/storage/v1` proxy and the key minter of the measurements. Tool versions are pinned in `package-lock.json` (firebase-tools 15.37.0, esbuild 0.25.0). Six transitive packages are raised to patched versions with npm `overrides` (`@grpc/grpc-js` 1.14.7, `@opentelemetry/core` 2.8.0, `uuid` 11.1.1, `glob` 14.0.6, `minimatch` 11.0.9, `@supabase/auth-js` 2.119.2): the first CI run's self-scan (trivy) reported 7 advisories against the lockfile, and no newer firebase-tools, firebase or supabase-js release removes them (npm audit offers only downgrades by a major version for the Firebase ones). Images are pinned by digest: `library/eclipse-temurin` 21.0.13.1+2 JRE (resolved 2026-11-23) for the emulator, with the runner's Node and the pinned firebase-tools mounted read-only, and ADR 0058's `supabase/postgres` 15.19.0.019 and `supabase/storage-api` v1.94.2. Each digest is pulled from Docker Hub and, on failure, from `mirror.gcr.io` (both have answered 429 to anonymous pulls, ADR 0058's record).
3. **The emulator's rules runtime** (`cloud-storage-rules-runtime-v1.1.3.jar`, 52.9 MB, which firebase-tools downloads from `storage.googleapis.com` at first start and checks by size and MD5) is downloaded by the job and checked against the SHA-256 that the pinned firebase-tools lists for it, before the emulator starts.
4. **One run per rule set, on one storage.** Firebase rules are replaced through the emulator's `PUT /internal/setRules`, which answers after the rules are loaded (no file watcher, no wait). Supabase policies are dropped and created with `psql`. Each set's file is also given to `--source` (`storage.rules`, or a migration), as in ADR 0058. The phrase `write test files` is typed through a pseudo-terminal (ADR 0044), as the writes job types its phrases; no flag can skip it (ADR 0058 item 4), and the job checks the prompt was shown.
5. **What each run must show**, in `gate.sh scan`:
   - its known answer, `testdata/known-answers/storage-<backend>-<set>.json` (14 files): the exact findings (`storage-public-write` at the bucket and folder), their count, and at least 90% of the fewest requests measured (ADR 0039);
   - its measured request count and result text, with the leftover file names (random each run) replaced by `NAMES` (`.github/gate/storage/results.txt`), so a run that tests fewer locations, refuses differently or stops reporting leftovers fails even when the findings stay the same;
   - from the storage's own listing (the emulator's owner token, or `storage.objects` in the database), read before and after: no object that was there before is gone, and the new objects are exactly the files the report names as left behind.
6. **Fixture names.** The rule sets are named `.rules.txt` (`firebase/README.md` says why): six of them are open on purpose, and as `.rules` files SiegeKit's own CI self-scan reported them as this repository's open rules (6 `backend-rules` findings), which fails CI (any finding fails it, owner 2026-11-19). The gate copies each to `storage.rules`. The Postgres password and JWT secret are random per job, not written in the script.
7. **The gate script is a file** (`.github/gate/storage/gate.sh`, `start`, `scan`, `logs`), not inline YAML, because the 7 runs per job share the same steps. It prints the engine, its cgroup version and whether it is rootless.

## Consequences

- A change to the storage write test that finds less, tests other locations, sends fewer requests or leaves an unnamed file fails the gate on both engines, against the real emulator and storage-api, not only the fake server of the unit tests.
- Time, locally with the images already pulled: starting the storage took 7 to 11 s (Firebase) and 10 to 46 s (Supabase, Docker and Podman); Firebase's 7 scans took 6 s in total. The two Supabase images are about 1.5 GB each unpacked. On CI (run 45192466982), starting the storage took 9 to 10 s (Firebase) and 38 to 39 s (Supabase), and the 7 scans 6 s (Firebase) and 15 to 17 s (Supabase); each job took 51 s to 1 min 44 s in all.
- Covered only: the emulator, not real Firebase Storage; storage-api behind a 30-line proxy, not the hosted Supabase gateway (still unverified, ADR 0058). Storage triggers are not in the fixtures (ADR 0058 measured them by hand).
- Open Cloud Storage rules in a real file are read by `backend-rules` in no gate: the self-scan no longer sees these fixtures, and the `firebase/quickstart-js` gate's answer covers Firestore rules (`firestore.rules:6` and `:10`), which go through the same parser (`internal/checks/backendrules.go`); its unit test has only a closed `storage.rules`. A test of open Storage rules in a real file is an item for the M2 milestone check.
- trivy's advisory data is downloaded at each CI run, so a new advisory in one of the fixture's ~690 npm packages makes the self-scan fail until it is raised or replaced. These packages run only in CI, never in SiegeKit.
- The fixtures need a pin change to follow a new firebase-tools, emulator runtime or storage-api; the known answers say which pins they hold for.

## Alternatives considered

- Keep the `.rules` names and give the self-scan a known answer that requires exactly these 6 findings: prototyped with `internal/knownanswers/check` on the local self-scan report (it works), but the answer must list all 9 self-scan checks (62 lines locally), be measured on CI on both engines, and change with every self-scan check or finding; ci.yml's exit test changes too.
- Restart the emulator for each rule set: its start (7 to 11 s in the runs above) seven times per job, for the same result as `setRules`.
- Copy the rules file and wait for the emulator's file watcher, as the hand measurements did: its "Change detected" line comes before the rules are loaded, so a fixed wait would be a guess.
- One job per rule set (28 jobs): the same checks, 7 times the image pulls.
- A single answer file per backend: the known-answer format holds one answer per check per fixture (ADR 0039); 14 small files keep it unchanged.
- Commit the bundled apps instead of building them: they are what esbuild makes from pinned SDKs; building in the job keeps the source readable and the lockfile the only pin.
- Run the emulator on the runner without a container: it would then not be measured on rootless Podman and Docker, as the other gate jobs' apps and ADR 0058's measurements are.
