# 0062. Logins that are page forms, and a right-password guard

- Status: Accepted (owner 2026-11-23 21:54 UTC, Porchlet fix plan PR B, decision D2 as recommended)
- Date: 2026-11-23
- Amends: [0030](0030-login-throttling.md) (item 1: how the login is given; item 3: one login with the right password; item 4: a changed redirect is a limit; item 6: the finding needs the guard, says only what was seen, and needs 20 attempts), [0055](0055-rate-limit-pages.md) (item 6: what spraying's first answer may be; items 5 and 6: the "not limited" findings' wording), [0036](0036-rate-limit-check.md) (item 6: what `rate-not-limited` claims, and 20 requests)

## Context

The owner's run against Porchlet (Next.js with all Supabase calls on the server, 2026-11-23) showed `login-throttle` can report a false finding. Measured on a local copy (Next.js 16.4.6, `@supabase/ssr` 0.12.7, Supabase Auth v2.198.0; record and scripts in the project files, `porchlet-fixes-2026-11-23/`):

- A Server Action login form (Supabase's own server-side login guide pattern) runs only when posted as `multipart/form-data` with the page's `$ACTION_ID_…` field, the way a browser without JavaScript sends it. An urlencoded or JSON post gets the login page back (200) and never runs. SiegeKit reported "Failed logins are not limited" (medium) while **0 logins reached Supabase Auth**.
- The same class: a Django 5.2 login (built-in `LoginView`, CSRF on) answers every post without its CSRF token and cookie with 403, right password or not; SiegeKit at 4e6f35e would have reported no limit on 403s (measured here: both answered 403).
- Supabase Auth's limit shows through such an app only in the redirect: the same 303, `Location: /error?code=over_request_rate_limit` instead of `/error?code=invalid_credentials`. SiegeKit read status, `Retry-After` and body words, not `Location`.
- Rails 8.1.4.1's generated login (`bin/rails generate authentication`, `rate_limit to: 10, within: 3.minutes`) and Laravel 12.73.0 with Breeze 2.4.2 (5 wrong logins per name and address) show their limit only on the page the login redirects back to, in a message the session cookie carries: a wrong login and a limited one get the same 302 to the login page. Found while verifying this ADR's first build on CI (4ab4374): it reported "no limit seen" on both while each app's own log or counter showed the limit (Rails: 10 password lookups for 16 logins; Laravel: its counter stopped at 5). Measured locally, 2026-11-23.

The owner chose (decision D2) to make SiegeKit prove its logins reach the login code by sending one login with the test account's right password first, instead of comparing a wrong login's answer with the page (measured: two answers to the same ignored login differ byte for byte, so that needs a fuzzy comparison whose error rate is unmeasured).

## Decision

1. **`--login-page URL`** gives the login as the form on a page, instead of `--login-url` (not both). The page is on the target's origin (ADR 0042) and may have a query. `--login-body` then names the form's fields as a form body, such as `email={user}&password={password}`: each field once, `{user}` and `{password}` in values only, no JSON. Mistakes are refused before any request.
2. **How the form is sent.** Before each login SiegeKit GETs the page with no cookie (redirects not followed; the first read must be 200) and reads it as a browser without JavaScript does, following the HTML standard's form submission, cut down to login forms: the form is the first whose controls include every named field; a `<form>` inside another is ignored and its end tag ends the outer one; the `form` attribute assigns controls; comments and the content of `script`, `style`, `title`, `textarea`, `template` and the like are not markup. The submit button is the form's first (its default button, what Enter presses), and its `formaction`, `formmethod` and `formenctype` win over the form's; its name is sent. Hidden and other fields keep the page's values (checked boxes, selected options, `textarea` text; disabled controls, file inputs and other buttons are left out); the named fields are filled in. The action resolves against `<base href>` and the page, must be on the target's origin, and may have a query; a `javascript:` action, a GET or `text/plain` form, or a disabled default button makes the check fail with the reason. The post is urlencoded or multipart as the form says, with `Origin` set to the target's origin and the cookies the page set (RFC 6265 domain and path matching). Each login starts with no cookie: a limit kept only in a cookie is no limit against an attacker. The tag reader is the served-files check's (ADR 0032), moved to `internal/htmltag` and shared. `login-spray` sends the form the same way.
3. **The right-password guard.** The check needs the test account's password in `SIEGEKIT_LOGIN_PASSWORD` (at most 1,024 bytes, no control characters, refused before any request). It sends one login with it first, then the wrong ones. Its answer is compared with the first wrong one by status, redirect (with random values left out, item 4) and the names of the cookies it sets; when they are the same, the check fails with the reason instead of reporting, because its logins may never reach the login code. Without the variable the check is skipped (`no-input`, the reason names it). The password is kept in memory only: never in the plan, report, audit log or messages (a CLI test checks all three), and no plugin's container can be given a `SIEGEKIT_` variable (`sandbox.CheckEnv`). A limit sign on the right-password answer is reported as already limited (perhaps from an earlier run), as for the first answer before.
4. **Limits seen in the redirect.** A wrong login answered with a 301, 302 or 303 to a URL on the target's origin is followed once, as a browser does: a GET with the cookies the login sent and those its answer set (a 307 or 308 is not followed: a browser would send the login again; the right-password login is not followed). A limit word on that page that the first wrong login's page did not have is a limit; at the first wrong login, a limit word the login page itself did not have means a limit already holds (or a warning: either way no report of no limit). A later answer whose `Location` differs from the first wrong answer's is a limit. Random values are left out first: each run of letters, digits and hyphens 8 or more long with a digit (a token, an ID, a time) becomes `*`; words such as `over_request_rate_limit` stay. With `--login-page`, the page read before each login is also read: a 429, 423 or 503 or `Retry-After`, a status other than 200 (a server error fails the check), or a limit word the first read did not have (a CAPTCHA that appears) is a limit; a form that disappears without such a sign fails the check.
5. **Spraying after an address limit.** A limit for the whole address can still hold when `login-spray` starts, so its first answer is the limited one and later ones look like the limit ending (measured: "limited after 14 attempts" read backwards). Spraying is given `login-throttle`'s result: a first answer of the same kind (status, redirect and limit words) as the one that showed the limit, and not of the normal kind, is a limit that holds for other names too.
6. **Results.** The finding names the wrong answer (status and redirect) and the right password's answer. The report's `requests` counts every request (page reads, followed redirects and the right-password login), and `input` names the form, its action, encoding and button.

7. **What "no limit" claims (issue #79).** A run of N wrong logins shows only that the app allowed N guesses, not that it has no limit: Porchlet's R1 run (2026-11-24) limits at the 6th failed login and got a medium "Failed logins are not limited … an attacker can keep guessing" from 5 attempts. The findings now say what was seen: `login-not-limited` is titled "No limit seen in N failed logins" and says an attacker can make at least N guesses, that many apps limit at 5 to 30 and NIST SP 800-63B allows at most 100 in a row for one account, and that a limit above N is not seen; `spray-not-limited` likewise ("No limit seen in N failed logins across accounts"). Fewer than 20 attempts (the default, ADR 0030) give no finding: the result adds "too few attempts to report a finding … run again with --login-attempts 20 or more". The owner extended this to the four other "not limited" findings, which make the same claim from the same N (owner 2026-11-24 16:11Z): `rate-not-limited` ("No rate limit seen in N requests", "anyone can call it at least N times in a row"; fewer than 20 `--rate-limit-requests` give no finding and the result says so), `reset-not-limited` ("No limit seen in N password-reset requests", "at least N reset messages", "at least N guesses at reset answers"), `signup-not-limited` ("No limit seen in N sign-ups", "at least N accounts in a row") and `code-not-limited` ("No limit seen in N wrong verification codes", "at least N guesses", NIST's 100); the reset, sign-up and code pages always send 20. Severities are unchanged. The limits measured so far are all refused by the 21st attempt or are Supabase Auth's (burst 30), where "no limit seen in 20" is still true: Porchlet 5 per account and address, 20 per address; Laravel 12 Breeze 5; Rails 8.1 generated auth 10; Juice Shop and Django `LoginView` none.

## Consequences

- Server Action logins (Next.js `formAction` buttons and `useActionState` forms) and CSRF-token logins (Django, Rails and Laravel measured) are tested; the false finding class "logins never processed" now fails with a reason on every login shape, and limits shown only after the redirect (Rails' and Laravel Breeze's) are seen: Rails limited after 10 of 15 attempts, Laravel after 6 of 10, where the first build reported no limit. On Laravel Breeze, `login-spray` reports no limit across 10 names, which is right: its limit counts each name and address together.
- A wrong login that redirects costs one more request (the Next.js `login` scan: 17 instead of 12).
- Every `login-throttle` run needs the test account's password, and logs in once with it (a new session, perhaps a "new sign-in" email). Runs without it are skipped. The CI gate's Juice Shop scan uses jim's password from Juice Shop's own seed data (`data/static/users.yml`).
- A login whose right and wrong answers differ only in the body (a 200 JSON `{"ok":true}` against `{"ok":false}`, no cookie) fails the check: a missed test, never a false finding.
- A limit shown only after a redirect in words outside SiegeKit's list (or in another language) is still missed, and a wrong-login message that already holds a limit word (such as "locked after 5 attempts") reads as a limit at the first login: a missed finding, not a false one.
- A redirect that changes by a short random value (under 8 characters, or with no digit), or by a counter (`?attempt=3`), reads as a limit: a missed finding, not a false one. None was seen in the apps measured.
- With fewer than 20 attempts the checks report no finding, only the result (issue #79): a person who sends 5 to spare the test account learns what was seen but gets no finding. The CI gate's form-login scans send 20 (Supabase Auth gets 21 logins, under its burst of 30).
- No run (50 attempts at most) can show that an app allows more than NIST's 100, or reach hosted Supabase Auth's default sign-in limit: its `/auth/v1/token` bucket holds 30 and refills at 0.5 a second per address (Supabase's documented 1,800 an hour, burst 30), so at one login a second the first 429 comes at about login 61. Measured from the throwaway project porchlet-test's edge logs on 2026-11-23: four direct runs got their first 429 at requests 37, 35, 11 and 31, as that bucket predicts (30 + 6, 30 + 5, 0 + 8 + 1.5, 30 + 1.5); its error code is `over_request_rate_limit`, as on the local image the gate runs. Porchlet's R1 scan 4 (41 logins in 39 s) therefore saw no limit, correctly.
- Not tested: forms built only by JavaScript (no `<form>`), forms whose login is not the first form with the named fields or not its first submit button (the guard then fails the check), `fieldset disabled`, and logins in several steps.
- The CI gate's `logins` job (Next.js 16.4.6 and Supabase Auth v2.198.0, both engines, both architectures) holds known answers for both form patterns, the ignored urlencoded post (must fail, and Supabase Auth must get 0 logins), and the limit seen in the redirect with spraying after it.

## Alternatives considered

- Compare a wrong login's answer with the page's own answer (D2's other option): measured byte differences on the same ignored login; needs a fuzzy comparison with an unmeasured error rate.
- Send the `Next-Action` header as Next.js's JavaScript does: a hand-built body got a 500, and the browser's form post works without it.
- A full HTML parser (`golang.org/x/net/html`): a new dependency for what the existing, fuzzed tag reader does for login forms.
- Carry cookies between logins: a limit kept in a cookie would show as a limit, though an attacker drops the cookie.
- Report "no limit" with a warning when a wrong login redirects and sets a cookie, instead of following the redirect: a false finding with a caveat is still a false finding on Rails and Laravel.
- Word the finding as "no limit seen in N" but report it at any N (issue #79 option B): Porchlet's 5-attempt run would still get a medium finding for a limit at the 6th.
- Allow up to 101 attempts, so a run can show NIST's 100 is exceeded and reach hosted Supabase's limit (issue #79 option C): up to about 100 s a run, and more risk of locking the test account (Devise locks after 20 by default).
- Choose among several forms or buttons by a flag: not needed by the apps measured; the guard catches a wrong choice.
