# 0055. Rate limits on reset, sign-up and code pages, and password spraying

- Status: Accepted (design: owner 2026-11-21, "the recommended design (answers by default, emails counted at a mail catcher when one is given)"; severities of items 5 and 6: owner 2026-11-22)
- Date: 2026-11-22
- Amends: [0036](0036-rate-limit-check.md) (item 5: what a first answer may be on these pages; item 6: a changed status is not "not limited"), [0030](0030-login-throttling.md) (spraying after a limit), [0029](0029-check-selection.md) (what `--profile quick` leaves out)

## Context

Item 3 of the ARTEX comparison (1.0 definition of done, item 3): an attacker abuses password-reset, sign-up and second-factor code pages, and sprays one password across many accounts to get past a per-account lockout. SiegeKit could test one such page only if the person typed its URL and body into `--rate-limit-url`, and `rate-limit` refused the 401 that reset and code pages give to a wrong guess. The owner approved the design on 2026-11-21 ([design](https://claude.ai/artifact/TqxngrSPwFyfQNyk27L9P9)): Q1 pages from flags or from the HAR recording, Q2 answers by default and emails counted at a mail catcher when one is given, Q3 read the limit number on code pages, Q4 20 sign-ups, Q5 spray only after `login-throttle` saw a limit. This ADR is the first of the design's three pull requests; the mail-catcher count and the CI gate's known answers follow (item 10).

The design left one part unmeasured: pages and bodies taken from a real browser recording. It was measured first (Evidence).

## Decision

1. **Four checks.** `reset-limit`, `signup-limit` and `code-limit` run `rate-limit`'s check (ADR 0036) once each on a password-reset, sign-up and second-factor code page, with their own check IDs so each has its own line, result and known answer. `login-spray` sends logins like `login-throttle`. All are SiegeKit's own, local targets only until M2.10, left out by `--profile quick` (amends ADR 0029), Linux only for now (ADR 0018). Each sends 20 POSTs, one per second (Q4), and stops at the first sign of a limit.
2. **Where the pages come from (Q1).** From `--reset-url`/`--reset-body`, `--signup-url`/`--signup-body` and `--code-url`/`--code-body`, checked before any request like `--rate-limit-url` (same origin, a single leading `/`, a query allowed, body at most 8 KiB, JSON when it starts with `{` or `[`, else a form). Without a page's flags, SiegeKit takes the first POST of that kind in `--har` (on the target's origin, a JSON or form body); a flag wins over the recording, later pages of the same kind are counted in the plan and not tested. A recorded POST is:
   - a **code page** when its path or query names a second factor (`2fa`, `mfa`, `tfa`, `totp`, `otp`, `two_factor` and the like), or names `verify`, `verification` or `challenge` and its body has a code field, and does not name `setup`, `enroll`, `enable`, `disable`, `delete`, `remove`, `regenerate` or `recovery` (those change the factor);
   - else a **reset page** when it names `forgot`, `recover`, `recovery`, `lostpassword` and the like, or `reset` with a password word (so `/cart/reset` is not one);
   - else a **sign-up page** when it names `signup`, `sign_up`, `register` or `registration` and no login word, or when its body has a password, the password again and no current password, and its path names no login, password, change, update or reset (Juice Shop's `POST /api/Users/`), or when its path ends in a collection of users (`users`, `accounts`, `members`, `customers` and the like) and its body has a password and a user name or email address and no current password (Mattermost's `POST /api/v4/users`).
   Words are split at anything but letters and digits and at camelCase, and neighbouring words are also joined.
3. **Bodies.** In a flag's body, `{wrong}` is filled with a new wrong guess each time (`siegekit-wrong-` and 20 random characters: never a real answer or code) and is required on a code page and allowed on a reset; `{new}` is filled with a new user name (`siegekit-new-` and 12 random characters) and is required on a sign-up, so each request makes a new account. A recorded body is turned into such a template: on a reset page every value but the user name, email address and CSRF token becomes `{wrong}`, so the recorded (right) answer and new password are never sent; on a code page the code field does (`code`, `otp`, `totp`, `passcode`, `pin`, names ending in `code`, and names starting with a second-factor word such as Juice Shop's `totpToken`), and a recorded page with no such field is not tested, with the reason; on a sign-up page the user name and email address get `{new}`, an address at `example.com` (reserved, and its null MX accepts no mail, RFC 2606 and 7505), and a recorded page with neither is not tested. No session or cookie is sent, as for `rate-limit`.
4. **First answers.** On a reset or code page a 401 or 403 is the answer to a wrong guess, so it is a valid first answer there (amends ADR 0036 item 5). A sign-up's first answer must be below 400: a refused sign-up made no account, so its limit cannot be tested and the check fails with the reason. 404, 405, 501 and server errors fail the check as in ADR 0036, and the reason names the flag or the recording.
5. **The limit number and window (Q3; the threshold awaits the owner's choice, card of 2026-11-23).** When a limit is seen, the number in `RateLimit-Limit` or `X-RateLimit-Limit` is read, and how long it lasts: `RateLimit-Policy`'s `w`, `RateLimit-Reset` or a `RateLimit` header's `reset`, `X-RateLimit-Reset` (seconds, or a Unix time as express-rate-limit sends it) or `Retry-After`; both are shown in the result. On a code page, the wrong codes allowed per window (the number, or else the wrong codes answered before the limit) times the windows in a day is compared with NIST SP 800-63B-4 section 3.2.2, which allows "no more than 100" failed attempts in a row before the factor is disabled: above 100 a day is a low finding, `code-limit-high` (CWE-307), whose message gives the attacker's odds for a 6-digit code by RFC 4226 section 6 (guesses / 10^digits). With no window in the headers, only a number above 100 is. The design's 10 had no source; a per-window 100 would miss 50 every 5 minutes, which the owner asked to cover (2026-11-23). A reset time is the window when the first request starts it (express-rate-limit, Juice Shop) and shorter otherwise, which overstates guesses a day for a fixed window that started earlier.
6. **Spraying (Q5).** `login-spray` runs right after `login-throttle`, and only when that saw a limit on the one account: the same number of logins to the same URL and body, each for a new invented user name (`siegekit-nobody-1` and on, at `example.com` when the test account's name is an email address) and all with one wrong password, read for a limit exactly as `login-throttle` reads it. No limit is a **medium** finding, `spray-not-limited` (CWE-307; owner 2026-11-22). When `login-throttle` saw no limit, or did not run or finish, it is skipped with cause `no-input` and the reason: one address that is never limited on one account cannot be limited across accounts.
7. **Results and findings.** As ADR 0036 item 6, with: no limit on a reset page is **low**, `reset-not-limited` (CWE-799), whose message says the answers do not show whether emails or texts were limited (Q2 A, until item 10); on a sign-up page **low**, `signup-not-limited` (CWE-799); on a code page **medium**, `code-not-limited` (CWE-307; owner 2026-11-22). A later answer that says so in words the first answer did not have (`too many`, `too often`, `locked`, `captcha` and the others `login-throttle` reads) is a limit, for `rate-limit` too: Ory Kratos 1.3.1 answers every wrong SMS code with 400 and, from the 6th, "The request was submitted too often". When a later answer's status differs from the first one's, with no 429, 503 or limit header, nothing is reported and the result says so: a changed status may be a limit. This also applies to `rate-limit`, whose result said "all answered 200" even when they did not (amends ADR 0036 item 6). `plugins[].input` names the page and where it came from (`(from --reset-url)` or `(recorded in a.har)`), and `result` says what the requests may have made: accounts named `siegekit-new-...`, or emails and texts (answers below 400).
8. **Safety.** The page checks and spraying are in the loopback confirmation of ADR 0023 (typed `yes`, or `--authorized-host`), whose warning names what they do: up to 20 reset requests and that many emails or texts to the address in them, up to 20 accounts and emails, up to 20 wrong codes, and logins for invented names. Reset bodies keep only the address the person gave or recorded; never put a real person's address in them.
9. **Order.** `login-throttle`, then `login-spray`, `rate-limit`, `reset-limit`, `signup-limit`, `code-limit`, then the other URL checks, so their traffic does not count against a limit these checks then report (ADR 0030).
10. **Later pull requests (design build plan).** PR 2: count emails at a mail catcher the person names (Mailpit), so a reset that answers the same each time but sends one email is seen as limited (Q2 B). PR 3: the CI gate's known answers on Juice Shop (reset and code limited, sign-up not limited) on both engines. Until then the Juice Shop gate lists the four checks as skipped for want of input.

## Consequences

- Sign-up tests leave up to 20 accounts named `siegekit-new-...` behind, and reset tests can send real emails or texts if the app is wired to a real provider (not measured: no app with a real provider was tested). The report says what was made.
- A reset page that answers the same to every request is reported as not limited even when the app limits its emails, until the mail-catcher count (item 10); the finding says so. Measured on Gitea.
- Not seen: limits above 20 requests, per IP address, or that only slow answers; pages that need a session the recording no longer holds (they fail); pages whose words or fields are not in the lists of item 2 (not found in the recording; flags still work); a code field with another name.
- Spraying is measured on the test app and on Mattermost (per-account lockout, no limit across accounts); Juice Shop and Gitea lock no account, so it is skipped there.
- A changed status is no longer reported as "not limited" by `rate-limit` either; on Juice Shop's product search every answer was 200 (ADR 0036), so the gate's answer is unchanged.

## Alternatives considered

- Probing a list of 30 common paths to find the pages (design Q1 C): not chosen; it finds no body, and on Juice Shop gave 5 false pages for 3 real ones (design measurement).
- One check ID for all pages: not chosen; one report line could not say which page was limited, and the known answers need each page's result.
- Sending the recording's cookies: not needed on the 6 measured pages, and it would send account A's session with requests that create accounts.
- Low severity for code guessing and spraying, like `rate-limit`: offered and not chosen (owner 2026-11-22); both let an attacker guess a credential, which `login-throttle` rates medium.
