# 0049. Replaying recorded writes as another account (access-control-write)

- Status: Accepted (design, owner 2026-11-21; build-time items 2b, 3b, 4b and 7, owner 2026-11-21, "Both fixes (recommended)" and "Both (recommended)" after the measurements below; items 2c and 2d and the recording checklist, owner 2026-11-21, "Guide + 2 additions" after the gap measurements)
- Date: 2026-11-21
- Amends: [0035](0035-access-control-replay.md) ("Not covered: state-changing requests"; item 4 is unchanged: `access-control` stays GET and HEAD only)
- Amended by: [0050](0050-method-calls-sent-as-post.md) (method calls sent as POST: reads, IDs in params, refusals inside a 2xx answer, IDs the client chose), [0051](0051-outsider-account-c.md) (account C, and the order C, no login, B)

## Context

`access-control` (ADR 0035) replays only GET and HEAD, so it cannot see one account changing or deleting another account's data. Item 2 of the ARTEX comparison asked for writes. The owner chose the recommended design on 2026-11-21 ([design](https://claude.ai/artifact/8devNYkvUihhY7JB2717oc)): Q1 tiers, Q2 re-create A's object, Q3 the HAR only, Q4 B and no login; local only, off by default, a second typed phrase.

The design's prototype (Python, hand-written JSON requests on Juice Shop v20.4.0 and Gitea 1.24.6's token API) found 5 of 5 real write leaks, 3 at high with no false alarm and 2 at medium, plus 4 false alarms at medium.

Measured while building, with the built Go code (2026-11-21, Claude's sandbox, Docker 29.10.0 rootful, cgroup v1; record in the project's shared files, `write-replay-build-2026-11-21.md`):

- **Real browser recordings work for JSON apps.** Juice Shop, Chromium recording made with Playwright (login, basket, address, card, review). The recorded answers are in the HAR, and the new object's ID (`data.id`) is in the create's answer, so "find the ID the write uses in an earlier POST's answer" finds the create. A new address and a new card both got ID 7, so the create whose path shares the most segments with the write's is taken first.
- **A's create can be refused the second time.** Juice Shop allows one basket item per product, so after the first replay's copy, A's create failed and the DELETE of a basket item fell back to the item A had deleted in the recording (404): a real leak was missed.
- **B replaying A's plain creates is noise.** B adding its own address or card is allowed by design: 2 false medium findings in the Juice Shop recording.
- **CSRF-protected forms.** On Gitea's web UI every write carries a CSRF token, in the body or in `X-Csrf-Token`. Sent with A's token, all 21 replays were refused with 400: nothing was tested.
- **GraphQL reads are POSTs too.** DVGA (`dolevf/dvga:latest`, image ID `040aa33c199d`), Chromium recording of two pastes and the paste lists: its 2 `query getPastes` requests were taken as writes and replayed, giving 2 false medium findings. GraphQL over HTTP also answers a refused operation with 200 and an `errors` list, so 2xx alone would count it as accepted (GraphQL over HTTP specification; not measured, no recorded app refuses one).
- **Gaps, measured (owner's question "any ways to close that gap?"; record `write-replay-gaps-2026-11-21.md`).** On Juice Shop, 11 real write flaws were confirmed by hand from the routes in `build/server.js` (B or no login acting on A's or shared data). The check as first built found 4 of them on the basic recording. With a fuller recording (A also edits a review, sends feedback and checks out), it found 8: 4 high and 4 medium, with no false alarm. Trying the PUT, PATCH and DELETE requests the recording did not make, on objects A read or made, found 2 more (B deleting A's feedback; a product changed by any account), with no request accepted wrongly; on Gitea's web UI those tries all answered 405. B's checkout of A's basket was medium only because A's basket was already empty after the recording; with A's earlier basket writes sent again first, A's read of the basket showed the change. Not taken, measured: the OpenAPI spec's write operations (Gitea: 874 requests per repository, 0 real flaws, 7 allowed by design of which 3 would read high; Juice Shop's spec has only `/orders`); routes named in the app's scripts (nothing beyond the tries); A reading the parent page after a POST (on Gitea, B's issue and comment, both allowed by design, would read high; raw pages differ on every read).
- **Successful form posts can answer 303.** 4 of the 13 Gitea web writes A recorded were answered with a redirect, not 2xx.

## Decision

1. **`access-control-write`** is SiegeKit's own check (ADR 0015), family `dast`, in `internal/authz` (`write.go`), for URL targets, **local targets only**: with `--deployed` the flag is refused and the check is skipped (`deployed-or-local-only`); `WriteCheck` itself refuses a deployed mode or a read-only configuration. It is left out of `--profile quick`. Linux only, like the other URL checks (ADR 0018).
2. **Writes come from the HAR file only** (Q3): with `--replay-writes` and `--har`, its POST, PUT, PATCH and DELETE requests to the target's origin, in order, without duplicates (same method, path and body), at most 50, bodies and headers as recorded (`replayHeaders`). Form fields without body text are counted and not replayed.
   - a. **A copy of A's object** (Q2). For each write, SiegeKit looks for an earlier recorded POST with a 2xx JSON answer holding an ID field (`id`, `_id`, `uuid`, `guid`, `number`, at most 3 objects deep) whose value the write uses: a path segment, a query value, or a body value at an ID-named key. Among several, it takes the one whose path shares the most leading segments with the write's, then the latest. Before each replay, A sends that create again and the write uses the new ID in its path, query and body. When no create is found, or A's create gives no ID, the write goes to A's recorded object; if B's replay of it is accepted (and it is not a POST without an ID), the request with no login is not sent for it, and the result says "not tested with no login".
   - b. **A deletes its copy** after each replay when the URL ends with the copy's ID and the replay did not already delete it (one DELETE as A). Juice Shop recording: finds the DELETE leak that (a) alone misses, and leaves no copy in A's account; +1 request per copy.
   - c. **Tries beyond the recording.** For each object A read (a recorded 2xx GET whose last path segment is an ID, static files left out) or made (a recorded create's collection plus the ID in its answer, GraphQL left out), SiegeKit adds the PUT, PATCH and DELETE requests the recording did not make on that shape of path (IDs replaced), at most 50, DELETE last. A PUT or PATCH carries A's own read of the object (inside `data` when the app wraps it) or A's create body; without a JSON body only DELETE is tried. They use the copy (a, b) when the object was made by a recorded create, go through the never-replayed list (5), are listed before the confirmation as "not in the recording", and their findings say so. Juice Shop: +2 real flaws (DELETE of A's feedback at high, PUT of a product at medium), 0 accepted wrongly; Gitea: 3 DELETE tries, all 405.
   - d. **A's earlier steps first.** For a POST whose path holds an ID that is not copied, SiegeKit finds A's earlier recorded writes (not DELETE) whose JSON body names that ID at an ID-named key, and does not hold it in their path (POST `/api/BasketItems` with `"BasketId": "6"` before POST `/rest/basket/6/checkout`), the last 3 of them. A sends them again before each replay. A then reads the longest recorded 2xx GET that is a leading part of the POST's path and ends with that ID (`/rest/basket/6`) twice before the replay and once after; when the two reads before differ, the read proves nothing (`Noisy`). Juice Shop: B's checkout of A's basket goes from medium to high; A's basket keeps the items sent before the replay with no login (listed in the result). Only for a POST: before a PUT on a product's reviews, the rule re-sent a basket item naming the same product (measured), and a PUT, PATCH or DELETE already reads its own URL.
3. **Who sends** (Q4): account B (`SIEGEKIT_SESSION_B`: A's headers without the session headers, plus B's) and no login (A's headers without the session headers). Without B, only no login.
   - b. **Plain creates are not sent as B**: a POST whose path holds no ID and not A's login name (`--har-user`), and whose body has no ID-named key with an ID value. B sending it makes B's own object. Juice Shop recording: 2 false medium findings fewer, no real case lost; it loses B tests of POSTs to resources named by something else, such as an organisation's slug.
4. **When a write was accepted, and how sure** (Q1, tiers): the replay is accepted when it answers 2xx.
   - a. **High** when it was a PUT, PATCH or DELETE, A read the same URL with 2xx before it, and A's read after it differs (status or bytes); or a POST with earlier steps (2d) whose object A read the same twice before and differently after. **Medium**, "check it by hand", for any other accepted replay.
   - b. A redirect (3xx) also counts as accepted when A's own recorded write was answered with a redirect too, this one does not lead to a login page (`login`, `logon`, `signin`, `auth`, `sso`, `oauth`, `authorize` in its path), and it does not only go where the request asked (its target is not a value of the request's query or form body). The last condition was added after the final Gitea run: Gitea's `/-/fetch-redirect` answers anyone with 303 to its `redirect` field and changes nothing, which gave 4 false medium findings with no login; with it, Gitea is back to the 4 medium findings of item 7.
   - Findings: `cross-account-write` for B (CWE-639 with an ID in the URL, CWE-862 otherwise) and `no-login-write` (CWE-306), at the recorded write's URL without the query. Messages give the method, path and statuses, never bodies. Findings at the same URL and CWE merge (the existing dedupe), so a PUT and a DELETE on one URL give one finding; the result lists both.
5. **Never replayed** (design safety rule 4): writes whose path or query names a login, logout, sign-up or registration, a password, a second factor (`2fa`, `mfa`, `otp`, `totp`, `twofactor`, `webauthn`, `passkey`), tokens, API keys or sessions, in any case, split at `-`, `_`, `.` and camelCase; and a DELETE whose last word (IDs left out) is `user`, `account`, `me`, `self` or `profile`. They are counted and named in the result. Login and logout are in the list because a browser recording always holds them (Juice Shop and Gitea, measured): replaying A's login as B or with no login logs in as A.
6. **Caps:** at most 50 recorded writes and 50 tries (2c), each sent as B and with no login: at most 10 requests per replay (A's create, up to 3 earlier steps (2d), A's reads before (1, or 2 for a POST with steps), the write, A's read after, a DELETE (2b) and a page GET (7)), so at most 2,000; one at a time at the run's local rate (100 per second). Measured: Juice Shop's fuller recording 199 requests, Gitea's 52.
7. **CSRF tokens.** A write carries a CSRF token when a header or field is named with `csrf`, `xsrf`, `authenticity_token` or `RequestVerificationToken`. Before sending such a write, the sender (B, or no login) loads a page (the recorded `Referer`, else `/`; `/` also when the `Referer` names an action, ADR 0048), takes the token the page gives it (a `csrf` meta tag, a hidden field, a `csrfToken:` script value, else a CSRF cookie) and its cookies, and sends it in place of A's token. Gitea web: 21 of 21 replays tested instead of 0; B refused on all 4 owner-only writes; 4 medium findings, all allowed by design (B's issue, comment and star on alice's public repository; a star with no login answered 204 and changed nothing); Juice Shop unchanged. +1 GET per CSRF replay. The result says how many writes went with the sender's own token, and how many went with A's because no page gave one (their refusals say nothing about access control).
   - a. **No GET to an action URL (ADR 0048).** A's reads before and after a replay are skipped when their URL names an action (ADR 0048's words), so such a write reaches medium only; `TestWriteCheckNoActionGET`.
   - b. **GraphQL.** A POST whose JSON body (or batch) has a `query` string is a GraphQL request. Queries and subscriptions (the operation `operationName` names, else the first; the `{ … }` shorthand is a query) are reads: they are counted and not replayed. A mutation is replayed like any write and named in the listing, the result and the finding's message (`POST /graphql (GraphQL editPaste)`); an unnamed mutation is named by its first field, plus the field inside it when the first takes no arguments (a namespace: Wiki.js 2's `pages { update(…) }` is `pages.update`). The lockout words (item 4) are also matched against these field names, so a GraphQL login (`authentication.login`) is never replayed. Its object's ID may be one level deeper in the create's answer (data, mutation, payload), so 4 levels are read, or 5 under a namespace (Wiki.js 2: `data.pages.create.page.id`); a batch of one is read as its one answer. A 2xx answer is a refusal when it has an `errors` list and no data (absent, or nothing but null and `__typename`), or when the data reports one: a `succeeded` or `success` field that is false (Wiki.js 2's `responseResult`), or a non-empty `userErrors` or `errors` list (Shopify's and Saleor's documented style, not measured). A batch is refused when every answer in it is. A persisted query sent by its hash alone is not recognised and stays a write. DVGA after the fix: the 2 queries not replayed; the 2 `CreatePaste` mutations with no login accepted (DVGA has no login at all). Wiki.js 2 (`requarks/wiki:2`, image ID `e4708eed80c0`, accounts alice and bob in a group allowed to write pages and comments; Chromium recording of a login, a page create, an edit and a comment, all sent as batches of one with no operation name): before this handling, the login was replayed with no login and answered "Login success", and 6 refusals were taken as accepted (6 false medium findings). After: the login not replayed; B's page edit (`PageUpdateForbidden`) and every no-login replay refused; B's comment on A's page accepted, 1 medium, which Wiki.js allows by design (any account with comment rights may comment); 14 queries not replayed; 9 requests. The page create's copy failed (Wiki.js refuses a second page at the same path), so A's recorded page was used. Every mutation shares the endpoint's URL, so its findings merge into one per CWE; the result lists each mutation.
8. **A person confirms, twice.** The "test accounts" question (ADR 0035 item 11) names `access-control-write` too. Then SiegeKit lists every write it will send and asks the person to type `change test data`, saying that it changes data in the app and to use a throwaway database or a snapshot. Without a terminal, or with other words, the check is skipped with cause `not-confirmed`; the read-only `access-control` still runs after "test accounts". No flag or environment variable skips either question; a program that gives SiegeKit a pseudo-terminal can type both (ADR 0044).
9. **The result says what changed**, so the person knows what to reset: the replays accepted (method, the path as sent, and who), the copies made and deleted again, A's earlier writes sent again (2d), the writes not tested with no login, the writes never replayed, and the CSRF note.
10. **Recording checklist.** The flag's help, the confirmation prompt and the agent guide tell the person to record every kind of change the app has: create, edit and delete each kind of object, send each form, finish a purchase. What A never did is tested only through the tries (2c).

## Evidence for the check as built

- Unit tests (`internal/authz/write_test.go`): `TestGraphQLOp` (names, namespaces, aliases, batches, the login's fields), `TestGraphQLRefused` (errors with no data, payload refusals, batches), `TestParseWritesGraphQLBatch` (a Wiki.js-shaped recording: the login under lockout, the update linked to its create five levels down), `TestWriteCheckGraphQL` (queries not replayed; a refusal with 200 and `errors` not accepted; an unchecked mutation on A's copy a medium finding); parsing (lockout, duplicates, the address-and-card ID collision, CSRF marks, the 50-write limit), the lockout words, ID replacement in path, query, JSON and form bodies, plain creates, redirects to login pages; the check against a test app shaped like Juice Shop (one item per product, an owner-checked card, own notes, a form that needs the sender's own CSRF token and answers 303), B's DELETE on A's recorded object, medium findings, the refusals for deployed mode and read-only configurations; `FuzzParseWrites` in CI. `cmd/siegekit/write_test.go`: the flags, both questions, the listing, the configuration (not read-only, local mode) and the report. The test app (`internal/runner`) gets carts that any account can change but only the owner can read or delete; `TestAuthzWriteFindsPlantedIssue` reports exactly the one planted change and leaves A's recorded cart untouched.
- Measured on local Juice Shop and Gitea with browser recordings: see Context, items 2b, 3b, 4b and 7, and the shared record.
- With items 2c and 2d, on fresh containers (2026-11-21, Docker 29.10.0 rootful, cgroup v1): Juice Shop's fuller recording (15 writes, 17 tries) gave 6 high (basket item change and delete, address change, review in A's name, checkout of A's basket, A's feedback deleted) and 4 medium (A's review edited, feedback in A's name as B and with no login, a product changed by B), all real, 10 of the 11 flaws, 199 requests; the 11th (a privacy request in A's name) has no UI, no spec entry and no script body. A product changed with no login is found as B's write: B's was accepted on the recorded product, so the no-login request is not sent for it (2a). Gitea's web UI: unchanged, 4 medium allowed by design, 3 tries all 405, 52 requests. DVGA: unchanged. `TestWriteCheckTriesAndSteps` covers a tried DELETE found on a copy, a checkout found high after A's earlier step, and the same checkout medium when A's read of the basket differs on its own.
- The labels ("real", "allowed by design") are Claude's, checked against each app's database or A's own reads; nobody else checked them.

## Consequences

- Writes between accounts get an automated check for the first time, on local targets, when the person asks for it.
- It changes data in the app for real: B's accepted writes stay (for example B's forged review in A's name on Juice Shop), and copies the app will not let A delete stay. The result lists them; the guide says to use a throwaway database or a snapshot.
- **Not covered:** writes the recording did not make, other than PUT, PATCH and DELETE on objects A read or made (2c); objects named by a slug, not an ID (the replay goes to A's real object); POST writes reach high only after earlier steps (2d), so on apps that write only with POST, such as Gitea's web UI, every hit is medium; multi-step flows whose steps do not name the object's ID in a JSON body (form bodies, IDs in the session); GraphQL access control was measured on one app with accounts only (Wiki.js 2: one owner-checked mutation refused, one allowed by design); GraphQL creates whose copy the app refuses (Wiki.js: same page path) fall back to A's recorded object; refusals reported in other payload shapes than those above are taken as accepted; WebSocket messages (not replayed); a PUT that adds to a list reads as high whenever the list changes, which would be a false high on an app where B may add its own entry (Juice Shop's review was real: B posted in A's name); apps that redirect back to a form after a failed write would give false medium findings under 4b (not measured).
- False-alarm rates on apps other than Juice Shop and Gitea are not measured.

## Alternatives considered

- **2xx alone, same-URL read alone, a marker in B's text** (Q1 options A, B, D): see the design. A: every finding needs a person; B: drops two real cases; D: 1 more false alarm and up to 202 more requests.
- **Using A's recorded object** for every replay (Q2 option B): 5 of 16 Juice Shop replays changed A's data, so 5 no-login tests would be skipped.
- **OpenAPI write routes** (Q3 option B), measured after the build: Gitea's API spec, 183 of 223 write operations fillable with alice's names, 874 requests per repository; 0 real flaws, 7 allowed by design (fork, issue, comment, watch, reactions), 3 of which would read high through the list read; Juice Shop's spec holds only `/orders`.
- **Routes named in the app's scripts**, measured: Juice Shop's script names 14 `/api` collections; listing them as A and trying PUT and DELETE on items with A's `UserId` found the feedback and address flaws the tries (2c) already find, nothing more, 86 requests, and needs the app's owner field.
- **A's read of the parent page after any POST**, measured: Gitea's pages differ on every read (render time, CSRF token, timestamps), and after stripping those, B's issue and comment on alice's public repository, allowed by design, would read high; so the parent read is only used after earlier steps (2d), with two reads before.
- **B only** (Q4 option B): loses the no-login write test.
- **Leaving CSRF-protected writes as "could not test"** (7): nothing tested on Gitea's web UI.
