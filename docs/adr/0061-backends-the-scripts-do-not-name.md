# 0061. Backends the app's scripts do not name

- Status: Accepted (fix plan for the Porchlet findings, PR A; owner decisions D1 to D6 approved as recommended on 2026-11-23 at 21:54 UTC, D1 is this ADR's item 3)
- Date: 2026-11-23
- Amends: [0037](0037-backend-live-check.md) (item 1: the kind can come from `--source`; item 3: a backend the scripts do not name; item 4: the key can come from the environment), [0058](0058-storage-write-test.md) (the same for `storage-write`), [0059](0059-storage-write-known-answers.md) (three more runs in the `storage` gate job)

## Context

`backend-live` and `storage-write` read three things from the scripts the app serves: whether the backend is Supabase or Firebase (when the host name does not say), the Supabase public key, and, for a backend not on this machine, the proof that it is this app's (its host appears in a served file). An app that calls Supabase only from its server, as in Supabase's server-side login guide for Next.js (the pattern the plan's test bed copied), serves none of these. The owner's run against Porchlet (Next.js and Supabase, every call on the server) failed with "cannot tell whether ... is Supabase or Firebase: the app's scripts name neither", and `--source` pointing at a repository with a `supabase/` directory did not help ([plan](https://claude.ai/artifact/6WWJukAaSHSu9pH5iARyfA), findings 1 and 2). This is a class, not one app: every server-only Supabase app gets no result from either check.

## Decision

1. **The key comes from `SIEGEKIT_SUPABASE_KEY`** when the scripts give none for this backend. An environment variable, not a flag, so it is not kept in shell history or shown in the process list. It is read only with `--backend-url` or `--storage-url`, before any lookup or request, and it must be a public key: an `sb_publishable_` key or a JWT whose role is `anon`. An `sb_secret_` key, a `service_role` JWT, a JWT with any other role (a user's session token) and anything else are refused with the scan's usage exit code and a message that never holds the key: a secret key reads past row-level security and storage policies, so its results would not be what anyone who loads the app can do. Surrounding white space is trimmed. An anon JWT that names another hosted project (`ref`) than the host's is refused for that check before any request.
2. **The kind comes from `--source`** when the host name and the scripts do not tell: Supabase when the repository has a `supabase/` directory with `config.toml` or a `.sql` file (`supabase start` needs `config.toml`), Firebase when it has `firebase.json` (the emulators need it), `database.rules.json`, `firestore.rules` or `storage.rules`. A repository with both, or neither, leaves the kind unknown, and the reason says so. For `storage-write`, the scripts are read again for that kind's bucket names. The report's input says "(from --source)".
3. **What ties a backend the scripts do not name to the app** (owner decision D1). The host is still typed in a terminal, as before (no flag skips it, ADR 0037 item 3, ADR 0044). Then SiegeKit sends one `GET /auth/v1/settings` with the key, on a read-only configuration, before any read or upload. It goes on only when the answer is 200 with Supabase Auth's settings (a JSON object with an `external` object): the project's API gateway accepted the key. For a server-only app the key is not public, so holding a key the project accepts shows access to the project. Any other answer fails the check with nothing else sent ("refused the key in SIEGEKIT_SUPABASE_KEY (GET /auth/v1/settings answered 401), so it is not this project's key"). With no key, the check fails as before, and the reason now says how to give one. A Firebase backend the scripts do not name is still refused: Firebase has no secret-free per-project key to check.
4. **Which key is used.** The key in the scripts when the scripts are tied to this host (it is on this machine, or they name it); otherwise `SIEGEKIT_SUPABASE_KEY`. When both exist and the scripts' key is used, the report's input says the variable was not used. A key from the variable is checked as in item 3 on every host not on this machine, also when the scripts name the host but carry no key: a wrong key would otherwise read as every table refused. On this machine it is not checked: a local stack can run without a gateway, as the CI fixture does.
5. **Never written.** The report's input says "public key from SIEGEKIT_SUPABASE_KEY" (or the served file's name), never the key; it is not in the console output, the reports or the audit log.
6. **CI known answers** (ADR 0059's `storage` job, Supabase, both engines, both architectures): three more runs on policy set s2 with a page that names no backend and serves no key (`app/so.html`), `--source` holding only `supabase/config.toml`, the bucket insert and the policy. `so-local`: the storage on this machine, the stack's anon key, no key check. `so-remote`: Supabase's own self-hosted API gateway (the Envoy image and config of `supabase/supabase`'s `docker-compose.yml` at commit 0af0e9a, files downloaded and checked by SHA-256, not copied) with Supabase Auth v2.198.0, reached at the runner's private address, which SiegeKit treats as not on this machine: the host and phrase typed, the project's publishable key accepted, then the uploads. `so-other`: the same with another project's publishable key: refused, nothing uploaded. Each run is checked like the others (known answer, `results.txt` with the address as `ADDR`, the storage's listing) and must not hold the key in its report or output.

## Consequences

- Every server-side Supabase app can be tested by both checks, on this machine or hosted, with the project's public key and the typed host.
- The hosted gateway gives the same answers as the self-hosted one: `GET /auth/v1/settings` answered 200 to the project's key, 401 to a made-up publishable key and 401 to no key, the same as the measured self-hosted gateway (owner's run, 2026-11-24). The hosted 200 holds Supabase Auth's `external` object (owner's PowerShell check of the parsed body with the project's key: `True`, 2026-11-24), so the key check accepts the project's key there. Unverified: both checks run end to end against a hosted project.
- The tie is the gateway's key check. A Supabase served without its gateway (Supabase Auth exposed directly, as measured) accepts any key there, so for such a backend the tie is only the typed host. Self-hosted Supabase ships with the gateway.
- Holding the project's public key is weaker proof than the app's scripts naming the host when the key is shared widely (for example in a public mobile app of the same project). The typed host remains the person's own confirmation.
- One more request to the backend for a key from the variable on a host not on this machine.
- The `storage` gate job's Supabase runs pull two more images (Envoy and Supabase Auth, pinned by digest, both with `linux/arm64` builds in their indexes) and download four config files from `raw.githubusercontent.com`. Locally the Supabase job's start took 11 s (Docker) and 14 s (Podman) with the images pulled, and its 10 scans 19 s and 33 s.
- Kind from `--source` covers apps whose repository has `supabase/` or Firebase's config files. A Supabase app with neither, on a non-Supabase host, still needs its scripts to say.

## Alternatives considered

- A `--supabase-key` flag: visible in shell history and the process list.
- A `--backend-kind` flag: `--source` already holds the answer in every repository that runs a local Supabase or Firebase stack; one input instead of two.
- For a backend the scripts do not name, allow only a local backend (D1's other option): loses every hosted server-only app, Porchlet's real shape.
- Check the key with `GET /rest/v1/`: the self-hosted gateway serves the OpenAPI root only to the service role (its `rest-v1-openapi` route allows only the service keys), and ADR 0037 records the same change for hosted projects (not checked against one), so a valid public key would be refused.
- Check the key with the first table read: a 401 there is also PostgREST's answer for a table the anon role may not read, so a wrong key and protected tables could not be told apart, and the reads would already be sent.
- Accept a secret key and warn: its results would be what the server can do, not what anyone who loads the app can do, and the key would sit in the environment of a tool that sends requests.
