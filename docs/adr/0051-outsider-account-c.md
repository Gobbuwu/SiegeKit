# 0051. Account C: an outsider to the spaces A shares

- Status: Accepted (owner 2026-11-22 06:29 UTC, decision card "Spec + server code (E2), with B": this ADR is option B, the first of three pull requests; build-time items 3, 4 and 5 are Claude's, measured below and brought to the owner with the pull request)
- Date: 2026-11-22
- Amends: [0035](0035-access-control-replay.md) (items 3, 4, 5, 9 and 11: who sends, what is reported, the typed question) and [0049](0049-write-replay.md) (item 3: who sends, and in what order)
- Amended by: [0052](0052-route-sweep.md) (C is also sent the routes swept from the API spec), [0074](0074-server-actions-and-rsc-prefetch.md) (item 2: writes are sent with no login first, then C, then B)

## Context

`access-control` (ADR 0035) and `access-control-write` (ADR 0049, 0050) send account A's recorded requests as account B and with no login. In apps where people share a space (a group chat, a direct message, a team, a project, a shared repository), the person usually picks a B who shares that space with A, because the recording only reaches A's data through it. Then B is allowed in by design, and nobody outside the space is ever tried. The owner asked on 2026-11-22 whether an outsider C can read or change A and B's conversation; it had not been tested.

Measured before the decision (record `outsider-shared-space-2026-11-22.md` in the project's shared files, Parts 1 to 4; Claude's sandbox, Docker 29.10.0 rootful, cgroup v1; built code `main` a41f725):

- Rocket.Chat 6.13.1 (`f245efa7c787`, with `mongo:8.0` `479e85ced54f`) and Gitea 1.24.6 (`2edc102cbb63`): replaying alice's recording with bob (a member) as B gave 10 findings allowed by design (Rocket.Chat 6, 2 of them high; Gitea 4, 1 high). With carol (outside the space) as B, every one of them was refused. 4 older false alarms were the same with either.
- An attacker-style sweep of every room route as carol (Rocket.Chat 122 routes, Mattermost 12.0.2 63 routes, files, live streams; owner 05:49 UTC: "think like how a hacker / AI (artex) would attack") found one real outsider leak, Rocket.Chat's `chat.getDeletedMessages`, which no first-party client calls. It is still in 8.9.1 and `develop`. Finding it needs a sweep of documented routes (pull request 2 of this decision), not the recording.
- A blind spot if B's lone access were hidden: Mattermost's default member role may rename a private channel, remove its members and archive it; Gitea's read-only collaborators may open issues. Both are by design, and both are access only a member has.

Options measured (record, Part 1 table): a guide only (A), account C with B's lone access shown as low (B), the same with B's lone access hidden (C), reads sent as POST (D), and a route sweep (E). The owner chose B with E2 (spec and server code) as later pull requests.

## Decision

1. **Account C** comes from `SIEGEKIT_SESSION_C`, read and checked like `SIEGEKIT_SESSION_B` (one `Name: value` header per line, at most 8 KiB, the same refused headers; a mistake is refused before any lookup or request, and the message names `SIEGEKIT_SESSION_C`). C is an account outside every space A shares: not in A's groups, conversations, teams or projects. C can be given with or without B. Headers C sets are removed from A's request for B and for no login, as B's are.
2. **Who sends, and in what order.** Reads: A, then C, then B, then no login. Writes, with C: C, then no login, then B; without C, B then no login as before (ADR 0049). Each sender gets its own copy of A's object where the recording shows how A made it (ADR 0049 item 2). A sender whose write is accepted on A's recorded object (no copy) stops the later senders for that write, as B stopped no login before ("not sent to every account"). C goes first so nothing B changes can make C's replay fail; no login goes before B so that the comparison in item 4 has an answer for every write C was refused on.
3. **What is reported.**
   - C gets A's data (reads: the rule of ADR 0035 item 5, with C in B's place) or C's write is accepted (ADR 0049's rules): `cross-account-read` or `cross-account-write`, at the tier B would get, and the message names account C and `SIEGEKIT_SESSION_C`. If B got the same answer, the message says so and B's replay adds no finding. For a write, if B's replay reached a higher tier (A's read changed after B's but not after C's), the one finding takes B's tier and says the proof is from B's replay.
   - B gets A's data or B's write is accepted, and C was refused: **low**, rule `b-only-read` or `b-only-write`, "Only account B can read (change) this data": B has access C lacks, expected if B is a member of a space A shares with it, a flaw if B should not have it. Same CWE as `cross-account-*`.
   - "C was refused" means C's replay was sent and got a clear answer: a status from 200 to 499 other than 429, that was not A's data (reads) or not accepted (writes), and for a write that needs a CSRF token, C carried its own (ADR 0049 item 7a). A 429, a 5xx, no answer, a write not sent as C, or C sent with A's stale CSRF token says nothing about access: B's finding keeps its tier, and its message says why C was not compared.
   - Without C, everything is as before.
4. **C's session must be seen to work.** An expired or mistyped C session is refused everywhere, which would lower every finding of B's. So no finding of B's is lowered unless C's session was seen to work: on at least one replay (for writes, one write sent both as C and with no login), C and the request with no login both answered, with different statuses, and C's answer was neither 401 nor a redirect. Otherwise B's findings keep their tiers, each message says C was not compared, and the result says C's session may have expired. An accepted write alone does not count: on Rocket.Chat an expired C session's `DELETE /avatar/room/<rid>` is accepted (the route answers anyone with the avatar), and the first version of this rule took that as proof and lowered all 4 of B's write findings (measured, see Evidence).
5. **Reports and the question.** The plan, the typed `test accounts` question ("accounts A (the HAR file's session), B (`SIEGEKIT_SESSION_B`) and C (`SIEGEKIT_SESSION_C`)"), the `change test data` listing, `plugins[].input` and `plugins[].result` name C. The read result counts "readable by account C or B" and "only by account B (low)"; the write result counts low findings. Each says which session variable is not set.
6. Limits are unchanged; with C each read replay sends one more request (at most 400 for 100 replays) and each write replay one more sender.

## Consequences

- Every run with C tests an outsider on what the recording reached, and the noise from a member B moves out of high and medium without being hidden.
- People give one more test account; the plan says when C is missing.
- **Not covered:** routes the recording did not reach (Rocket.Chat's `chat.getDeletedMessages` leak is found only by the route sweep, pull request 2); IDs the recording did not hold (guessing Rocket.Chat room IDs is a separate item); live streams and socket methods; reads sent as POST (option D, covered by the sweep). A role or group only B has that the app trusts wrongly is reported as low, not high: the person must read the low findings. An app that answers an expired session differently from no session (not 401 and not a redirect) would pass item 4's check; none of the four measured apps does.
- Measured on rootful Docker 29.10.0 and rootless Podman 4.9.3, both cgroup v1; the CI gate runs the Juice Shop part on rootless Podman 5.7.0 and rootful Docker, cgroup v2.

## Alternatives considered

- Option A (guide only), option C (hide B's lone access), D and E: see Context and the record. C would have hidden the Mattermost and Gitea member powers.
- Keeping B's finding at its tier when C was refused, with a note: the 10 by-design findings would stay high and medium.
- Order C, B, no login for writes: when B is accepted on A's recorded object, no login is not sent, so item 4 has nothing to compare for that write (the first build's unit test showed it); no login before B costs one request per write B is accepted on.
- Treating any acceptance of C's write as proof that C's session works: wrong on Rocket.Chat (item 4).
