# 0050. Method calls sent as POST in the write replay

- Status: Accepted (build: owner 2026-11-22, "Merge #59, fix in next PR"; item 4b: owner 2026-11-22 05:01 UTC, "Fresh ID for B", chosen from three measured options)
- Date: 2026-11-22
- Amends: [0049](0049-write-replay.md) (items 2, 3b and 4)

## Context

`access-control-write` (ADR 0049) takes every recorded POST as a write. Some apps send every action, reads included, as a POST that names a method in its body. Measured on Rocket.Chat 6.13.1 (`rocketchat/rocket.chat:6.13.1`, image ID `f245efa7c787`, with `mongo:8.0` `479e85ced54f`; Claude's sandbox, Docker 29.10.0 rootful, cgroup v1; Chromium recording made with Playwright of alice logging in, sending a message in `#general` and editing it):

- Every method goes over HTTP as `POST /api/v1/method.call/<method>` (or `method.callAnon` with no login), with a DDP method message inside a JSON string: `{"message":"{\"msg\":\"method\",\"id\":\"16\",\"method\":\"sendMessage\",\"params\":[…]}"}`. The WebSocket carried only `connect`, a resume login, subscriptions and typing notices.
- With the check as merged in #59 (`main` 0e52b83), 46 POSTs of the recording were taken as writes, and 16 no-login replays were reported as medium findings, all false: 14 `POST /__meteor__/dynamic-import/fetch` (Meteor's code-bundle fetch) and the anonymous `public-settings/get` and `license:isEnterprise`, which are reads.
- Account B sent nothing: the message ID is inside the DDP string, so the edit (`updateMessage`) looked like a plain create (ADR 0049 item 3b) and was not sent as B.
- The answer to a refused method is HTTP 200 with the error inside the DDP string: B's `updateMessage` on alice's message answers `{"message":"{\"msg\":\"result\",…,\"error\":{\"error\":\"error-action-not-allowed\",…}}","success":true}`. On 2xx alone it reads as accepted.
- The browser chooses a new message's `_id` and sends it in `sendMessage`; the answer gives it back. Sent again with that `_id`, Rocket.Chat answers 200 with no result and makes nothing. So A's copy (ADR 0049 item 2a) failed, B's edit went to A's recorded message, whose text already matched the recorded edit, and Rocket.Chat answered that unchanged edit with success before its permission check: 1 false medium for the edit and 1 for B's send, which made nothing.

## Decision

1. **Method calls** (`rpcOp`, `internal/authz/write_rpc.go`). A POST body is a method call when it is a DDP method message inside a JSON string field `message` (`"msg":"method"` and a `method` name), or a JSON-RPC request: an object or a batch of objects with a `method` string and either a `jsonrpc` member or both `params` and `id` (JSON-RPC 1.0). A body with only a `method` field (a payment method, say) is a plain JSON body. GraphQL (ADR 0049 item 7b) is read first and is not affected.
2. **Reads are not replayed.** A call reads when every method in it reads by name (`readName`): the name is cut into parts at every character other than a letter or digit, and a part's first word (split at camelCase) is `get`, `list`, `fetch`, `find`, `search`, `load`, `query`, `count`, `lookup`, `describe`, `is`, `has` or `can`, and no write verb (ADR 0048's action words plus `send`, `set`, `mark`, `write`, `post`, `put`) starts a part or follows `or` or `and`: `public-settings/get`, `loadHistory`, `license:isEnterprise`, `eth_getBalance` and `getImportProgress` read; `sendMessage`, `updateMessage`, `readMessages` (marks a room read), `getOrCreateRoom` and `rooms:delete` do not. A write verb later in the name is a noun there (`getImportProgress`, `getRoomJoinCode`): the first version vetoed any write word and replayed 5 Rocket.Chat reads (see Evidence). A POST that is not a method call or GraphQL is a read when its last path segment that is not an ID names a read in the same way (`/__meteor__/dynamic-import/fetch`, Gitea's `/-/fetch-redirect`). Both are counted, and the result names the first 5. The lockout words (ADR 0049 item 5) also apply to method names (`login` sent to `/rpc`).
3. **IDs in params.** For a method call, object IDs are looked for, and replaced in a copy, only in the call's params (the DDP message inside the string, encoded again), never in the envelope's own `id`, which numbers the call. A create's new ID is read in the call's result (the DDP message's `result`, or JSON-RPC's `result`); when the result is a bare number or string and the method's name starts a part with `create`, `add`, `new`, `insert` or `make`, the result is the ID (Kanboard's `createTask` answers `{"result":1}`). When several recorded creates gave the same ID, a write is linked to the one whose method's last word is the noun of the key that holds the ID (`task_id`, or `id` in `updateTask`, goes to `createTask`), before the latest one; on a fresh Kanboard project the project, the task and the comment all get ID 1. The plain-create rule (ADR 0049 item 3b) reads the params.
4. **IDs the client chose.** A recorded POST whose answer gives back an ID that its own body held at a key of the same name (`_id` sent, `_id` answered), and that appears nowhere earlier in the recording, made an object under an ID the client chose.
   - a. A's copy of such an object (ADR 0049 item 2a) is made with a fresh random ID of the same shape (a new version 4 UUID for a UUID; otherwise each digit and letter replaced by one of the same kind). An ID seen earlier names an object that exists, so a POST that sends it changes that object and is replayed as recorded.
   - b. When such a create is itself replayed (B's or the no-login send), it carries a fresh ID too, and that ID does not count as naming another object for the plain-create rule. **Owner's choice** (decision card in the project thread, 2026-11-22 05:01 UTC: "Fresh ID for B"); the two alternatives are below, all three measured.
5. **Refusals inside a 2xx answer.** A write answered 2xx is not accepted when the answer is JSON with a top-level `success` that is false (Rocket.Chat's REST style; any write), when a DDP call's answer has an `error` in the DDP message, or when a JSON-RPC call's answer has a non-null `error` (JSON-RPC 2.0 specification; a batch when every answer in it has one). The DDP and JSON-RPC shapes are measured (Rocket.Chat's `updateMessage` refusal; Kanboard's "Method not found" and "Invalid params" answers are 200 with an `error`). The `success` false shape is tested only in unit tests: 8 refused Rocket.Chat REST writes by B (`chat.update`, `chat.delete`, `chat.pinMessage`, `chat.react`, `channels.setTopic`, `users.update`, `chat.starMessage`, `subscriptions.read`) all answered 400 with `success` false, so no measured app sends it with a 2xx.
6. Findings and the listing name the method when the path does not already end with it: `POST /rpc (method note.update)`.
7. **Socket fallback transports are not replayed.** SockJS's XHR transport (`/<prefix>/<server>/<session>/xhr`, `xhr_send`, `xhr_streaming`, `eventsource`, `htmlfile`, `jsonp`, `jsonp_send`) and Engine.IO polling (`?EIO=…&transport=polling`) carry a socket session's messages, including logins and subscriptions, tied to a session that is gone at replay time. They are counted and not replayed. When Rocket.Chat's WebSocket failed in one fresh recording, the browser fell back to SockJS and 37 such POSTs were taken as writes, including a DDP `login`, and replayed as 37 false medium findings (44 requests; 1 medium and 7 requests after).

## Consequences

- On apps that send actions as method calls, reads are no longer reported as writes, edits reach account B, and refusals inside a 200 answer are seen.
- POST-only apps still never reach high: A's reads on such apps are method calls too (`loadHistory`), and A does not send them before and after a replay.
- **Not covered:** methods named without a read verb that only read (they are replayed: a false medium at most); methods named with a read verb that change data and no write verb (not replayed); calls nested inside another call's params (Odoo's `call_kw` with the model method inside); refusal shapes other than those in item 5; JSON-RPC over GET; copies the app cannot delete with a DELETE on their URL stay in A's account (every Rocket.Chat copy); access control of reads sent as POST is not tested by either check.
- The word lists are measured on two method-call apps: every method in Rocket.Chat 6.13.1's client bundle (290) and every procedure in Kanboard v1.2.48's JSON-RPC API (160), each checked against the server code (see Evidence). Of these, 3 Rocket.Chat methods named as reads can write and are not replayed (`getStatistics` with refresh, `cloud:getOAuthAuthorizationUrl`, `livechat:getNextAgent`), and reads named without a read verb are replayed (Rocket.Chat's `browseChannels`, `spotlight`, `roomNameExists` and others; Kanboard's `downloadProjectFile`, `downloadTaskFile`): a false medium at most. False-alarm rates on other method-call apps are not measured.
- Method IDs in an array under a plural key (`task_ids: [1]`) are not matched by noun; such a write goes to the latest create with that ID (not measured on a real app).

## Alternatives considered

- **Path only** (`/method.call/<name>`, `/rpc`): misses JSON-RPC at other paths and DDP behind other routes; the body shape names the protocol.
- **Any read verb anywhere in the name**: `targetList` or `blacklistUser` would read; the first word of each part is closer to how methods are named.
- **Item 4b, keeping A's ID for B's send**: keeps a test of B overwriting A's object by reusing its ID, but Rocket.Chat ignores the reused ID and answers success, so the finding is false and nothing is written.
- **Item 4b, a fresh ID for B's send plus one more send with A's ID, checked by A reading the object back**: keeps the overwrite test without a false finding where a read exists. Measured by hand on Rocket.Chat 6.13.1: B's `sendMessage` with A's message `_id` answered 200 with no result; A's `chat.getMessage` before (twice) and after, and the database, showed the message unchanged. But the recording holds no read of a single message (A's reads are `loadHistory` method calls, which are not replayed), so SiegeKit would have no read to check with on this app, and the extra send would end unchecked. Cost: 1 more request per create with a client-chosen ID, plus 3 reads where a read exists.
- **Treating a DDP answer with no `result` as a refusal**: Rocket.Chat's successful `updateMessage` and `deleteMessage` answer with no result too (measured by hand).
