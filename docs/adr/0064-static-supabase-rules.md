# 0064. Static Supabase rules and one definition of a test

- Status: Accepted (PR E of the Porchlet fix plan, approved by the owner 2026-11-23 21:54 UTC with decisions D1 to D6 as recommended; this PR's own choices are listed under Consequences for the owner's review)
- Date: 2026-11-23
- Amends: [0011](0011-app-logic-and-ai-checks.md) item 3 (what `backend-rules` reads), [0034](0034-weak-passwords.md) (one more SQL pattern; the test folders move to a shared package), [0053](0053-routes-from-server-code.md) item 2 (the route reader's test folders and files), [0058](0058-storage-write-test.md) item 9 (done here), [0059](0059-storage-write-known-answers.md) item 2 (the policy sets are named `.sql.txt`)

## Context

The owner ran SiegeKit on Porchlet, a Next.js and Supabase app (record `porchlet-m0-findings-2026-11-23.md` in the project files). Four of its findings are about the static rules:

- **SK-4, a false positive.** `backend-rules` read every `.sql` file under `supabase/`, including `supabase/tests/database/000_baseline.test.sql`, a pgTAP test that runs inside a rolled-back transaction and is never deployed. `weak-passwords` skipped test folders, so two checks disagreed on what a test is. The same `isSupabasePath` filter fed `--source` table names to `backend-live`.
- **SK-5.** `weak-passwords` missed `crypt('password123', gen_salt('bf'))` in `supabase/seed.sql`, the way Supabase seeds create users.
- **SK-6.** `backend-rules` knew only "a table created without `enable row level security`". It missed RLS disabled in a later migration, `using (true)` policies, grants to `anon`, and views, which read their tables with the owner's rights.
- **SK-7.** Nothing read `supabase/config.toml`, where Porchlet has the CLI defaults `minimum_password_length = 6` and `enable_confirmations = false`.

ADR 0058 item 9 left two more static gaps here: Supabase storage policies (0 of the 6 open policy sets found) and a Firebase write rule whose only condition is a file size.

Two outside facts shape the design. Supabase's database linter, splinter, is the reference list (`supabase/splinter` at `cc529aa`, lints 0007, 0010, 0013, 0016, 0024). And Supabase changed its default grants ([changelog 45329](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)): "On May 30, 2026 this setting starts to become the default for all new projects", and "On October 30, 2026 the setting will be applied it to all existing projects"; since then new tables in `public` "require an explicit opt-in (via a Postgres grant)", existing tables "keep their current grants", and self-hosted is "Not affected". So whether `anon` can reach a table now depends on the project, and grants in migrations matter.

## Decision

1. **One definition of a test** (`internal/testpath`). A path is a test when a folder is named `test`, `tests`, `testdata`, `fixtures`, `__tests__`, `spec`, `e2e` or `cypress` (any case), or ends in `.tests`, `unittests`, `functionaltests` or `integrationtests`, or the file is `*.test.*`/`*.spec.*` for JavaScript and TypeScript (`.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`, `.mts`, `.cts`), `*.test.sql` (pgTAP), `*_test.go`, `*_test.py`, `test_*.py`, `*Test(s).java|kt|php|cs` or `*_spec.rb`: the union of the lists `weak-passwords` and the route reader of ADR 0053 had. `weak-passwords` (skipped and counted, as before), `backend-rules` (not read), `--source` reading for `backend-live` and `storage-write` (rules and migrations not read; OpenAPI files are still read wherever they are) and the route reader all use it. The route reader keeps its own non-test skips (`client`, `.meteor`, build caches).
2. **`backend-rules` replays the migrations.** The `.sql` files under a `supabase/` folder (tests left out) are read in name order, the order Supabase applies them, statement by statement, after comments and string contents are blanked. A small model keeps the tables, views and materialized views of each schema, row-level security on or off, the policies of each table, and what `anon`, `authenticated` and `public` were granted or revoked. It follows `create table`, `create [or replace] [materialized] view ... with (...)`, `alter table ... enable|disable row level security`, `alter table|view ... rename to`, `alter view ... set|reset (security_invoker)`, `drop table|view`, `create|alter|drop policy`, `grant|revoke ... on [table] NAMES|all tables in schema S`, and `alter default privileges [for role postgres] [in schema public] grant|revoke ... on tables`. Temporary tables and objects outside `public` are not exposed. A `do $$ ... $$` block is read like any other text; DDL inside a function body is too (it runs only when called; accepted, as before).
3. **Rules on the final state.**
   - `supabase-table-without-rls` (high, unchanged): a `public` table that never had RLS enabled.
   - `supabase-rls-disabled` (high, new): RLS enabled and later disabled; the location is the `disable` statement.
   - Both say how many policies the table has (they do nothing while RLS is off, splinter 0007), and neither is reported when the migrations revoke every privilege from `anon` and `authenticated` (splinter 0013 also needs a privilege).
   - `supabase-policy-always-true` (new): a permissive policy on a `public` table with RLS on whose deciding expression is literally `true` or `1=1` (any parentheses or case; splinter 0024's patterns). Which expression decides follows PostgreSQL, measured on 16.15: SELECT and DELETE use `USING`; INSERT uses `WITH CHECK`; UPDATE needs `USING` and checks the new row with `WITH CHECK`, or with `USING` when there is none; `FOR ALL` uses both; a missing clause lets nothing through. Severity by who and what: anyone (`anon` or `public`) writing (insert, update, delete) is **critical**; any signed-in user updating or deleting every row is **high**; any signed-in user inserting is **medium**; anyone reading every row is **low** (splinter leaves SELECT out as "often used deliberately for public read access"; SiegeKit keeps it, low, because a private table opened this way leaks every row); a signed-in user reading is not reported. Restrictive policies and roles other than `anon`, `authenticated` and `public` are not reported, nor a role the migrations revoked that privilege from.
   - `supabase-view-bypasses-rls` (high, new): a view in `public` without `security_invoker` on, at creation or by a later `alter view ... set`; `create or replace view` without `WITH` turns it off again (measured). Splinter 0010.
   - `supabase-materialized-view-exposed` (medium, new): a materialized view in `public` (it cannot have RLS). Splinter 0016.
4. **Grants are reachability, not findings of their own.** A grant to `anon` alone is not reported: for an old or self-hosted project it changes nothing, and RLS still decides. Instead each rule asks whether `anon`, `authenticated` or `public` can still use the privilege at the end: the latest grant or revoke on the relation itself, or a later `... on all tables in schema` one (which reaches the tables, views and materialized views that existed then, measured), or the default privileges the migrations set before it was created (only those for `postgres`, the role migrations run as, in `public` or all schemas). With none of these, the project's default applies, which SiegeKit cannot see, so it reports and the message says that projects whose objects postdate Supabase's 2026 change need an explicit grant; when a grant in the migrations is what opens it, the message says so.
5. **Storage policies** (`supabase-storage-policy-open`, new; ADR 0058 item 9). A permissive policy on `storage.objects` is open when its deciding expression never checks who is asking: no `auth.uid()`, `auth.jwt()`, `auth.role()` or other `auth.*()` call, no `current_user`, `session_user`, `current_role` or `current_setting(...)`, and no call to a function SiegeKit cannot read (such a function might check). `bucket_id = '...'`, `storage.foldername(name)`, size and name checks and the other listed functions do not count. The same command rules and severities as item 3 apply, except that reading is not reported (`bucket_id = 'avatars'` for SELECT is Supabase's own public-avatar example; listing public buckets, splinter 0025, needs the bucket's `public` flag and is left for later).
6. **Firebase rules that never check who is asking** (`firebase-rule-without-auth`, new; ADR 0058 item 9). An `allow` with a condition that never mentions `request.auth`, directly or through a function of the same file that does (the call graph is followed), lets anyone do it. It is reported for every write operation in it (critical, as an open write), and for a read only when the condition also reads no stored data (`resource`, `get()`, `exists()` and their `After` forms, directly or through a function), so Firestore's time-limited "test mode" (`if request.time < timestamp.date(...)`) is found and `resource.data.public == true` is not. `if false` is not reported; no condition or `if true` stays `firebase-public-access`.
7. **`crypt()` seed passwords** (SK-5). In `.sql` files only, `crypt('LITERAL', ...)` (also `extensions.crypt`) is a password set, judged by ADR 0034's rules (list, length 12, user name). A non-literal first argument (`crypt(new.password, ...)`) is not.
8. **`supabase/config.toml` auth settings** (SK-7). Only values written in the file count. `[auth] minimum_password_length` below 8 is `supabase-auth-short-passwords`, **low** (NIST SP 800-63B-4 section 3.1.1.2: passwords used alone must be "a minimum of 15 characters", and even those used only with a second factor "a minimum of eight characters"). `[auth.email] double_confirm_changes = false` is `supabase-auth-email-change-unconfirmed`, **low**. `[auth.email] enable_confirmations = false` is `supabase-auth-email-unconfirmed`, **info**, because it is what `supabase init` writes for local development (the CLI's init template at `supabase/cli` `ce767aa` has `enable_confirmations = false` and `minimum_password_length = 6`). An empty `password_requirements` is **not** reported: the same NIST section says verifiers "SHALL NOT impose other composition rules". The file sets up the local stack and, with `supabase config push`, a hosted project, so these stay low or info.
9. **The gate's storage policy sets are named `.sql.txt`**, as the Firebase rule sets already are, so CI's self-scan (`--fail-on info`) does not read six deliberately open policies as this repository's migrations; `gate.sh` copies them to `supabase/migrations/1.sql` as before. They are also this check's known answers (`TestStorageGateSets`).

## Consequences

- Every Supabase repository scanned gets the new rules; most CLI projects get one info finding for `enable_confirmations = false`, and apps with public catalogues get low findings for their `using (true)` reads.
- Choices made in this build, for the owner's review: the severities of item 3 (anyone reading every row is low, not medium); grants as reachability rather than findings (item 4); storage reads not reported (item 5); `enable_confirmations = false` info and an empty `password_requirements` not reported (item 8); `double_confirm_changes = false` added (item 8).
- The model is text, not a database: statements built at run time (`execute format(...)`), objects created by extensions, `search_path` changes and schemas exposed besides `public` are not followed. A function called in a storage policy is assumed to check the caller.
- Not covered yet: public buckets that allow listing (splinter 0025), `SECURITY DEFINER` functions callable by `anon` (splinter 0028), `auth.users` exposed through a view (splinter 0002), and policies that use `user_metadata` (splinter 0015). Views are not added to the `--source` table list for `backend-live` (PR A's area).
- The definition of a test now also hides fixtures in `spec/`, `fixtures/` and `cypress/` from `backend-rules`; a repository that keeps its real migrations or rules under such a folder is not checked (none in the 40 repositories above).

## Alternatives considered

- **Read only `supabase/migrations/` and `supabase/schemas/`** (the owner's suggested root fix for SK-4): fixes Porchlet but loses `supabase/schema.sql`-style files that apps paste into the SQL editor, and leaves the two checks with different ideas of a test.
- **Report every grant to `anon`**: noise on every project created before Supabase's change, where the grant changes nothing.
- **Splinter's exact SELECT exclusion and missing-clause rule**: the first hides a private table opened to everyone; the second reports policies PostgreSQL shows let nothing through.
- **Run splinter itself on a database built from the migrations**: needs a PostgreSQL in a container for a static check, and 3 of 21 example apps' migrations did not apply to a plain PostgreSQL (missing `pg_cron`, `pg_net`, `pgsodium`).
