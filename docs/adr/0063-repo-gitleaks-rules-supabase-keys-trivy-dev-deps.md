# 0063. The repository's Gitleaks rules, Supabase key rules, Trivy development dependencies, and checks left out of a run

- Status: Accepted (Porchlet fix plan PR D, owner approval of 2026-11-23 21:54 UTC, decisions D1 to D6 as recommended; D5: scan Trivy's development dependencies. Owner card of 2026-11-23 22:02 UTC: "Read Trivy's JSON instead")
- Date: 2026-11-23
- Amends: [0013](0013-run-storage.md) (the comparison with the last run), [0039](0039-known-answers-and-engine-parity.md) (a new known-answer fixture)

## Context

The owner's run of SiegeKit on Porchlet (Next.js and Supabase, every Supabase call on the server) found four gaps in the secret and dependency checks (record: `porchlet-m0-findings-2026-11-23.md` in the project files):

- **SK-1.** `gitleaks-history` ignored the repository's `.gitleaks.toml`. Cause, read in gitleaks 8.30.1's source and measured: Gitleaks takes `--config`, then `GITLEAKS_CONFIG` (a path), then `GITLEAKS_CONFIG_TOML` (the file's content), then `.gitleaks.toml` in the scanned folder, then its defaults. The plugin set `GITLEAKS_CONFIG_TOML` to add its `env-file-committed` rule, so the repository's file was never read. The report did not say which rules applied.
- **SK-2.** Neither Gitleaks scan has a rule for Supabase's new keys. A `sb_secret_` key was caught only by Porchlet's own rule, or by Gitleaks' `generic-api-key` when the line happened to hold a word such as `key =`.
- **SK-3.** Trivy left development dependencies out (no `--include-dev-deps`), and the report did not say so. On Porchlet that is 359 of 416 lockfile entries. A planted minimist 1.2.5 (development) was not reported.
- **SK-9.** After `--only trivy`, the comparison said "3 not checked again because their check did not run to completion". Those checks had been left out on purpose, not stopped.

## Decision

1. **Both Gitleaks scans build one configuration file and pass it with `GITLEAKS_CONFIG`** (`internal/runner/gitleaks.go`). The file is the repository's `.gitleaks.toml` as it is, or `[extend] useDefault = true` when there is none, followed by SiegeKit's rules (`run.gitleaksRules` in the manifest). The sandbox mounts it read-only at `/siegekit/config.toml`. The report's `input` names what applied: "the rules in the repository's .gitleaks.toml and SiegeKit's rules …" or "Gitleaks' default rules and SiegeKit's rules …". Rules:
   - The repository's file is **copied in front of SiegeKit's rules, not extended with `[extend] path`**. Gitleaks follows at most two `[extend]` levels, so a repository file that extends another file which uses the defaults would lose the default rules without a word.
   - `GITLEAKS_CONFIG` is used rather than `--config`, because `--config` changes the path Gitleaks keeps as its configuration and the repository's `.gitleaks.toml` would then be scanned as an ordinary file.
   - The repository's file is read without following a link, up to 1 MiB, as UTF-8 text without NUL. A link, a folder, a larger file or another encoding fails the check and says why, so the check never runs without rules the repository asked for.
   - A repository rule with the same id as one of SiegeKit's fails the check and asks for it to be renamed, because Gitleaks keeps one rule per id without a warning.
   - `.gitleaks.toml` is listed in both plugins' `repoIgnores` (the report already says the repository's file can hide findings).
   - The manifest checks `gitleaksRules`: Gitleaks with `targets: ["repo"]` only, at most 16 KiB of text, one `id = "…"` per `[[rules]]`, no duplicate ids, and no `GITLEAKS_CONFIG` or `GITLEAKS_CONFIG_TOML` in `run.env`.
2. **Two Supabase rules in both scans** (SK-2):
   - `siegekit-supabase-secret-key`: `\b(sb_secret_[A-Za-z0-9_-]{20,})`, entropy 3, high. The Supabase CLI's fixed local secret key (supabase/cli v2.121.0, `packages/stack/src/Defaults.ts`) is public and left out. It is written as a pattern with one character as a class, early in the key, so that the key itself is not in SiegeKit's files and the rule does not match its own pattern: with the class at the end, SiegeKit's self-scan reported the pattern in both manifests as a secret key (measured).
   - `siegekit-supabase-publishable-key`: the same for `sb_publishable_`, reported as **info** with its own message: the key is meant to be public, and what protects the data is Row Level Security on every table it can reach. The CLI's local publishable key is **not** left out: leaving it out lets Gitleaks' `generic-api-key` report it as a high leak on a `…_KEY=` line instead (measured, below).
   - `env-file-committed` stays in `gitleaks-history` only. In the tree scan it would report ignored local `.env` files.
3. **Trivy writes its JSON report with `--include-dev-deps --list-all-pkgs`**, and a new parser (`internal/trivy`, parser `trivy-json`) converts it (SK-3, D5). It keeps what Trivy's SARIF output gave (rule id, title, message, severity from the severity source's CVSS v3 score, location, help link), so fingerprints do not change, and adds the CWE IDs. A finding in a development dependency ends with a sentence saying so: not part of the built app, but it runs on developer machines and in builds and CI. The dependency is found by Trivy's package UID, so a development and a production copy of the same version are told apart. SARIF cannot carry this: Trivy's SARIF output has no field for it.
4. **Comparison** (SK-9): a finding gone from this run whose every reporting check was left out by `--only`, `--skip` or `--profile` is listed as **"not run this time"** (`notRun` in `report.json`, its own list in the HTML report). "Not checked again" is kept for checks that could not run or did not complete. Neither is counted as fixed, and both stay in the baseline for the next comparison.
5. **A planted repository in the gate** (gate job `planted`, `.github/gate/planted/make.sh`, known answer `planted-secrets.json`): the cases of the owner's run, built at run time with keys made from a hash, so that no key is stored in SiegeKit's repository. A secret key in the tree and one committed then deleted, a token only the repository's `.gitleaks.toml` knows, a service_role JWT, publishable keys, a committed `.env`, an ignored `.env.local` holding the CLI's local keys, and lodash 4.17.20 (production) and minimist 1.2.5 (development). Gitleaks and `dotenv-gitignore` must match exactly, Trivy must include both CVEs. The job also checks that both Gitleaks scans name the repository's rules as their input and that only minimist's finding says it is a development dependency. It runs on both engines and both architectures, like the other gate jobs.

## Consequences

- A repository's own Gitleaks rules now apply to its history too, and every Gitleaks result says which rules applied. A repository `.gitleaks.toml` that is a link, too large, not UTF-8, or defines a rule id SiegeKit also uses fails the check with the reason, where it was silently ignored by the history scan before.
- A repository rule that matches the same secret as a SiegeKit rule reports it twice. The repository rule is kept: it may be meant to differ, and the cost is a duplicate, not a miss.
- **Not fixed here, for the M2 milestone check:** the Supabase CLI's local secret key is still reported as a high `generic-api-key` finding on a line such as `SUPABASE_SECRET_KEY=…`, as it was before this change (the planted `.env.local:1`). Leaving it out under every rule needs a global `[[allowlists]]`, which makes Gitleaks refuse repository files that still use `[allowlist]` (measured above). The same holds for the older Supabase demo JWTs that local stacks used, which Gitleaks' `jwt` rule reports (not measured).
- The tree scan reads files git ignores, such as `.env.local`, as before.
- Development dependencies add findings: on the gate repositories 2,349, all marked. Each says why it still matters. pnpm lockfiles before version 9 are not covered. Trivy's source sets the development flag for npm, Yarn, pnpm 9, Bun, Poetry, uv, Composer, Gradle, Dart, Julia and Maven, but only npm, Yarn, Bun and uv were measured; the report's "Not tested" entry says so.
- Trivy's JSON report is larger than its SARIF report; both are limited to the same size as before (`sarif.MaxSize`).
- **Shallow history is another cause.** The M2 check item "shallow gitleaks-history" is not SK-1: CI checks out SiegeKit with depth 1, so the self-scan's history scan sees one commit, and SiegeKit does not say when a repository is shallow. That stays on the M2 milestone check list; this ADR does not change it.

## Alternatives considered

- **Extend the repository file with `[extend] path`**: loses the default rules when the repository file extends another file (measured).
- **`--config` instead of `GITLEAKS_CONFIG`**: the repository's `.gitleaks.toml` would be scanned as a file.
- **Keep Trivy's SARIF and say only "development dependencies are scanned"** (offered on the owner's card): a person could not tell which findings are in the built app. The owner chose the JSON report.
- **A global allowlist for the CLI keys**: breaks repository files with `[allowlist]` (measured). Left for the M2 milestone check with the demo JWTs.
- **An allowlist for the CLI's publishable key**: turns an info finding into a high `generic-api-key` one (measured).
- **List development dependencies under "Not tested" instead of scanning them** (the findings' other suggestion): rejected by D5.
