# 0035. The access-control check: replaying a recording as another account

- Status: Accepted
- Date: 2026-11-20
- Amends: [0011](0011-app-logic-and-ai-checks.md) item 1 (how requests are found, what is replayed, what counts as a finding)
- Amended: 2026-11-21, item 11 (typed confirmation that the accounts are test accounts; owner decision on Q5)
- Amended by: [0044](0044-typed-confirmations-limit.md) (what the typed confirmation can stop), [0047](0047-recorded-requests-to-zap.md) (the recording also goes to `zap-active`, and the typed question covers it)

## Context

ADR 0011 item 1 plans a two-account test: crawl as account A, replay each request as account B and with no login, and report answers that come back with the same data. It left open where the requests come from, how B's session is given, and what "the same data" means. The owner answered the M2.7 design questions on 2026-11-20 ([design](https://claude.ai/artifact/UjmsK3MmQ4btjaPg5427ar)): first "i want the claims to be measured before making a decision", then, after the measurements below, "since they're all backed by tests and proven working, let's go with them" (answers 1a to 9a). Two more decisions came after the check was built and measured (items 7 and 8 below). This ADR records answers 1a to 6a and those two; 7a (rate limits) and 8a (live backend rules) get their own ADRs with M2.7b and M2.7c (answer 9a).

Measured before the decision (2026-11-20, local OWASP Juice Shop v20.4.0, the CI gate's image):

- **Crawling as A does not work on a single-page app.** ZAP's AJAX spider given A's `Authorization` header and cookie found 361, 3,227 and 2,859 URLs in three runs, and none of the 4 requests that leak data between accounts: the app stayed logged out. ZAP's Access Control add-on is not in the pinned `zap-stable` 2.17.0 image.
- **A naive rule is noisy.** 17 GET requests replayed as A and B: "B gets the same answer as A" matched 11, of which 4 were real leaks (`/rest/basket/{id}`, `/api/Users/{id}`, `/api/Users`, `/api/Complaints`). Adding "a request with no login is refused" and "the answer holds data" matched exactly those 4. "No login gets 200" matched 6, all public by design.
- **Similarity scores cannot separate them**: all 11 equal answers were byte for byte identical, so the rule compares bytes.

## Decision

1. **`access-control`** is SiegeKit's own check (ADR 0015), family `dast`, for URL scans, in `internal/authz`.
2. **Requests come from a recording** (answer 1a): `--har FILE`, a HAR file the person records in their browser while using the app as account A (at most 64 MiB, a regular file). SiegeKit keeps the GET and HEAD requests to the target's origin, in order, without duplicates and without static files (scripts, styles, images, fonts, media), at most 100. It keeps their headers except those the transport or browser owns (`Host`, `User-Agent`, `Content-Length`, connection and transfer headers, `Accept-Encoding`, cache validators, `Sec-*`, `Proxy-*`, HTTP/2 pseudo-headers). Requests on other origins, other methods, duplicates and those over the limit are counted in the result. When an OpenAPI spec is available (`--openapi`, or found at a default path on local targets, ADR 0025), its JSON GET routes without path parameters are added under its base path, with A's session headers from the last recorded request that has any. YAML specs add none.
3. **Account B's session** (answer 2a) comes from the environment variable `SIEGEKIT_SESSION_B`: one `Name: value` header per line, at most 8 KiB, such as `Authorization: Bearer ...` and `Cookie: token=...`. It cannot set `Host`, `User-Agent` or the other headers above. Without it, only requests with no login are tested, and the plan and result say so. Mistakes in the HAR file or the variable are refused before any lookup or request.
4. **What is sent** (answer 3a). Only GET and HEAD, on every target including deployed ones and in `--profile quick`, so no confirmation is asked beyond the target's own, except that the accounts are test accounts (item 11). Each request goes first as A (as recorded). If A does not get a 2xx answer, nothing more is sent for it. Otherwise it goes as B (A's headers without the session headers, `Authorization`, `Cookie`, `X-Api-Key`, `X-Auth-Token`, `X-Access-Token`, `X-Session-Token` and any header B sets, plus B's headers) and with no login (A's headers without the session headers). SiegeKit sends them itself from the host to the pinned address (`egress.SendHeader`, read-only, no redirects followed, at most 2 MiB per answer), one at a time at the run's request rate (100 per second local, 10 deployed). At most 300 requests.
5. **When B can read A's data** (answer 4a): B's answer has the same 2xx status and the same bytes as A's, the request with no login was refused (401, 403 or a redirect), and the answer holds data. A JSON answer holds data when, outside the keys `status`, `message`, `msg`, `result`, `error`, `code`, `ok` and `success`, it has a non-empty array, a non-zero number, `true` or a non-empty string; any other non-blank answer holds data. Finding `cross-account-read`, CWE-639 when the URL holds an ID (a number, a UUID or 16 or more hex digits) and CWE-862 otherwise. It is **high** (answer 5a) when the URL holds an ID or the answer holds A's login name, and **medium** otherwise, with a note to check it by hand (item 8).
6. **When anyone can read A's data** (answer 6a): the request with no login gets A's exact answer, it holds data, and it contains A's login name, given with `--har-user NAME` (any case). Without `--har-user` this is not reported, and the result says so. Finding `no-login-read`, CWE-306, **medium** (item 8; answer 5a made it high).
7. **When anyone can read secrets** (owner, 2026-11-20, on the `/rest/memories/` miss below: "that miss seems like a serious and common issue", then "Measure, then add to #43"). The answer to the request with no login is a 2xx JSON answer with a field whose name, in any case and without `_`, `-` and spaces, is one of `password`, `passwd`, `pwd`, `passwordHash`, `hashedPassword`, `encryptedPassword`, `passwordSalt`, `salt`, `totpSecret`, `otpSecret`, `mfaSecret`, `twoFactorSecret`, `secret`, `clientSecret`, `apiSecret`, `secretKey`, `privateKey`, `apiKey`, `accessToken`, `refreshToken`, `sessionToken`, `authToken`, `resetToken`, `passwordResetToken`, `deluxeToken`, `ssn`, `socialSecurityNumber`, `cardNumber`, `cardNum`, `cvv` or `cvc`, anywhere inside, and that holds a value: a number other than 0, or a string without spaces that is not masked (`*`, `•`, only `x`) or a word such as `null`, `redacted` or `hidden`. Generic names such as `token` and `key` are left out: a public CSRF token is by design. Translation files (paths with `i18n`, `locale`, `locales`, `lang`, `langs`, `translations` or `l10n`) are skipped. Finding `no-login-secret`, **high**, CWE-200 (OWASP [API3:2023](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)); the message names the fields, at most 5, never their values. It does not need `--har-user` or B. Secrets only logged-in accounts get are not reported by this rule: in the sample those were either the account's own (a 2FA setup secret, runner registration tokens) or answers every account gets the same, which rule 5 reports.
8. **Severity by confidence** (owner, 2026-11-20, "Split by confidence", chosen over keeping every finding high or dropping `no-login-read`). After the measurement on Gitea and Memos below, `cross-account-read` stays high only with a sign that the answer is A's own (an ID in the URL, or A's login name in the answer), and `no-login-read` is medium, because public pages name their authors by design.
9. **Reports.** Findings are at the request's URL without its query. Messages give the method, path, status and size, never the answers' content or any header. The plugin entry gives `input` (the HAR file's name, the number of recorded requests, the spec's routes, whether B was given) and `result` (requests replayed, how many each rule reported, and the counts of what was not replayed). A result where B was refused on every request suggests B's session has expired.
10. Like the other URL checks it runs only on Linux for now (ADR 0018).
11. **A person confirms the accounts are test accounts** (owner, 2026-11-21, Q5: "a typed confirmation that accounts A and B are test accounts", approved after being told that the replay order protects results, not account A). Before any replay, SiegeKit names the sessions it will use and asks the person to type `test accounts` in a terminal. Without a terminal, or with other words, `access-control` is skipped with cause `not-confirmed` (ADR 0041) and nothing is sent for it; the other checks still run. No flag or environment variable skips the question (`--yes` and `--authorized-host` do not), as for deployed targets (ADR 0005). An assistant that follows the guide cannot confirm it; a program that gives SiegeKit a pseudo-terminal and types the answer can (ADR 0044). Threat model T25.

## Evidence for the check as built

- Unit tests (`internal/authz`): HAR and session parsing, the data rule, IDs, the check against a test server shaped like Juice Shop (a basket any account reads, a user list, answers that differ per account, an empty list, a public list, a profile readable with no login), B refused, cancellation, spec routes, secret fields (masked, empty, translation and nested cases), severity by confidence; `FuzzParseHAR` in CI. The test app (`internal/runner`) gets an order any logged-in account can read, an order that checks its owner, orders that differ per account, a profile readable with no login and a member list with password hashes readable with no login; `TestAuthzFindsPlantedIssues` reports exactly the three planted issues.
- Measured on local Juice Shop v20.4.0 with the built check (2026-11-20, two new accounts; record in the project's shared files, `access-control-measurement-2026-11-20.md`):
  - **A HAR recorded in Chromium with Playwright 1.63.0** while A logged in, filled the basket, saved an address and a card, and opened 16 pages: 28 requests replayed, 80 sent. Reported 1, true (`/rest/basket/7`, A's basket).
  - **A hand-made HAR of 20 API requests:** 60 requests sent, 1.2 seconds. Reported 5, all true (`/rest/basket/7`, `/api/Users/26`, `/api/Users`, `/api/Complaints`, `/api/BasketItems`).
  - **The CI gate's setup** (a fresh container, two new accounts, a hand-made HAR of 10 requests): 30 requests sent, 4 reported, all true (A's basket, A's user record, the user list, the complaints). A's new basket is empty but still reported: B reads its record, with A's user ID. The gate expects exactly these 4.
  - Every replay of the first two runs was labelled by hand: 6 reported, 6 true, 0 false. Not reported, and correct: answers scoped per account (addresses, cards, profile, whoami), empty answers for both accounts (order history, wallet), a 400 for no login on a public price, and public lists. One miss: `/rest/memories/` gives anyone every memory's full user record, password hashes included, but it does not hold A's login name (rule 6). Rule 7 was added for it.
- **Rule 7 before it was built** (a Python prototype, 38 Juice Shop GET routes, each with no login and as a new account): 4 answers with secret fields, 3 real (`/rest/memories/`; `/rest/user/authentication-details/` and `/api/Users` to any logged-in account) and 1 by design (`/rest/2fa/status`, the account's own setup secret). Limiting the rule to answers with no login keeps the real one with no login and drops the one by design; the two logged-in leaks are answers every account gets the same, which rule 5 reports.
- **On apps that are not deliberately vulnerable**, with the built check: Gitea 1.24.6 (all 229 GET routes of its OpenAPI spec, in three HAR files; a public repository, organisation, OAuth app, webhook and release) and Memos 0.25.1 (24 GET routes; an OAuth identity provider with a client secret). Labelled by hand:
  - `cross-account-read`: 6 true (Juice Shop 5, Memos 1: a normal account reads the identity provider's secret), 4 false (Gitea: both new accounts' identical default settings, bob's own permission on a public repository, a public organisation's membership, the public repositories alice watches).
  - `no-login-read`: 0 true, 3 false (Gitea's public commits carry the author's e-mail; Memos's public profile).
  - `no-login-secret`: 2 true (Juice Shop's password hashes; Memos's OAuth client secret given to anyone, the known [CVE-2025-65797](https://osv.dev/vulnerability/GHSA-99m2-qwx6-2w6f), fixed in 0.25.3), 0 false (no hit on Gitea's 229 routes).
  - With item 8, high findings in this sample are 6 true and 1 false (Gitea's watched repositories name alice); medium ones are 2 true and 6 false.
  - The CI gate's HAR includes `/rest/memories/` and expects exactly the one `no-login-secret` finding there.
- The labels are Claude's; nobody else checked them.

## Consequences

- Access control gets an automated check for the first time; without `--har`, it is not tested, and the report's "Not tested" list says so.
- **Not covered:**
  - requests the recording did not make: in the browser run, the user list, complaints and basket items were never requested, so 4 of the 5 leaks found from the hand-made list were not tested;
  - IDs other than the recorded ones (no guessing of other users' IDs), and OpenAPI routes with path parameters;
  - state-changing requests (POST, PUT, PATCH, DELETE);
  - answers that change on every request (timestamps, tokens), which never match byte for byte;
  - data readable with no login that neither holds A's login name nor has a field named like a secret, such as other users' names and addresses;
  - secrets given to logged-in accounts that differ between A and B, such as a user's own password hash returned to that user;
  - leaks between roles when B's answer differs from A's even though B should get nothing.
- The person must record a HAR and give B's session, which needs two test accounts they own (as ADR 0011 said). A HAR holds A's session; SiegeKit only reads it, but the file should be deleted after use. `docs/agents.md` tells AI assistants this.
- A short public answer that both accounts get and that a request with no login is refused (for example a price shown only to logged-in users) would be reported. The sample had none.
- Medium findings were mostly false in the sample (2 of 8 true): they need a person to look. On a real app with many public pages, `no-login-read` can be noisy.
- The labels come from one reviewer on three apps (one deliberately vulnerable). False-positive rates on other apps are unmeasured; the M2 milestone check triages again.

## Alternatives considered

- **Crawling as A with ZAP's AJAX spider:** found none of the 4 leaks on Juice Shop in three runs (measured above).
- **"B gets the same answer" alone:** 11 reported, 4 real, in the design measurement.
- **Similarity scores instead of equal bytes:** the equal answers were identical, so a score adds nothing and allows false matches.
- **Every finding high** (as answered in 5a): 8 of 15 true in the sample, with 7 false alarms at high.
- **Secret fields in logged-in answers too:** in the prototype, one of the three extra hits was the account's own 2FA setup secret, shown by design; on Gitea, five were each account's own runner registration token.
- **ZAP's Access Control add-on:** not in the pinned image, and it needs ZAP contexts and users set up by hand.
