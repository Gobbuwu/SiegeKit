- Date: 2026-11-22
- Amends: [0035](0035-access-control-replay.md) (item 2: the headers spec routes carry; the sweep on local targets), [0051](0051-outsider-account-c.md) (what C is sent)

## Context

`access-control` replays account A's recording as accounts C and B and with no login (ADR 0035, 0051). It tests only what A's browser called. Rocket.Chat's `chat.getDeletedMessages` gives any logged-in account the deleted-message IDs of any room whose ID it knows, in 6.13.1 and still in 8.9.1 and `develop`; no first-party client calls it, so no recording holds it (record `outsider-shared-space-2026-11-22.md`, Parts 3 and 4, in the project's shared files). Only a list of the app's routes reaches it: its API spec or its server code. The owner chose both (E2), in two pull requests; this is the spec half.

Rocket.Chat (12 files) and Mattermost publish their specs in YAML only. SiegeKit had no YAML reader and no Go library dependency. Measured options (record `spec-sweep-build-2026-11-22.md`): a vendored library (384 KB, builds offline), a converter in a pinned container, a hand-written YAML subset reader (Rocket.Chat's spec alone has 815 block scalars and 614 inline maps), or JSON specs only. The owner chose the vendored library.

The first measurement of the built sweep on Rocket.Chat 6.13.1 found nothing: every swept route answered A with 401. Spec routes (ADR 0035 item 2) and swept routes carried only SiegeKit's list of session headers, so `X-Auth-Token` went without `X-User-Id`, which Rocket.Chat needs beside it.

## Decision

1. **Where.** On local targets only, with a spec from `--openapi` or a default path (ADR 0025), after the `test accounts` confirmation (ADR 0035 item 11). The plan says so before the confirmation. Deployed targets keep ADR 0035's parameterless JSON spec routes only. GET only: the sweep reads; writes from the spec are a later item and will need A's read-back first (Rocket.Chat's `starMessage` answers `success:true` and changes nothing).
2. **Reading the spec.** OpenAPI 3 or Swagger 2.0, JSON or YAML. YAML is read with `go.yaml.in/yaml/v3` v3.0.6, vendored in `vendor/` (listed in `THIRD_PARTY.md`), through its node tree so a date such as `2018-12-12T00:11:22.345Z` stays a string. At most 2,000,000 nodes are visited, aliases included, and at most 128 levels deep, so a spec built to expand is refused. Every GET route is taken with its path and query parameters, path-level and operation-level, and `$ref` parameters inside the same document (`#/components/parameters/...`, `#/parameters/...`). YAML merge keys (`<<: *base`) are followed as yaml.v3 decodes them, keys written in the mapping winning. A route the spec does not fully describe, a `$ref` to another file or to a name the document lacks, or a `{name}` in the path that no path parameter declares, is not sent and is counted ("with a parameter the spec does not describe"): the sweep does not read other files, and sending it half filled or with literal braces only earns a 404.
3. **IDs come from A's recording.** `ParseHAR` reads each recorded request's query, body and answer and keeps the values shaped like IDs (numbers, UUIDs, 16 or more hex digits, or 10 to 64 letters, digits, `_` and `-` with at least one letter and one digit) under the field or parameter name they appeared under: at most 8 per name, 64 in all. Objects and queries are read in key order, so the same recording always gives the same IDs. Values under time fields (`create_at`, `ts`, `_updatedAt`, `created_unix`, names with `date` or `time`) are not IDs.
4. **Filling a route.** A path parameter, and a required query parameter whose name asks for an ID (`roomId`, `user_id`, `rid`, `key`...), take the IDs A's recording showed under the same name or an alias (`roomId` with `rid`, `channel`, `group`...), at most 3 per route. An ID-named path parameter no alias matches takes any of A's IDs; a path parameter whose name is not an ID (`{owner}`, `{repo}`) takes none. With no ID to fill it, the route is not sent and is counted ("needing an object ID the HAR file never showed"): the sweep does not guess IDs. Other required query parameters take the spec's example, or `0`, `false`, or `1970-01-01T00:00:00.000Z` for a date-like name or format, or the empty string. Optional parameters are left out.
5. **No address parameters.** A route whose required parameter asks for an address (format `uri`, `url`, `uri-reference` or `iri`, or a value with `://` or starting with `//`) is not sent and is counted: the app would fetch it, and spec examples point at other sites.
6. **Headers.** Spec routes (ADR 0035 item 2) and swept routes carry every header of A's last recorded request that has a session header, not only the session headers, as a copy. Recorded headers are already limited to those a replay may send. C, B and no login get them as for a recorded request (ADR 0051 item 1).
7. **Limits.** Routes whose URL names an action are skipped (ADR 0048). At most 500 filled routes (`MaxSweep`), on top of the 100 recorded and spec requests; each is sent up to four times. The largest measured spec, Mattermost 12.0.2's, fills 370 (371 when measured, see Evidence).
8. **Judging and reporting.** Unchanged: swept routes are judged by the read rules of ADR 0035 and 0051, at the same tiers. A 429 is counted and not compared (ADR 0051 item 3); the result says how many answers were 429 and that coverage may be incomplete. The result counts the swept routes and each reason a route was not sent.

- Findings and their severities were the same on Docker and Podman for Mattermost and Gitea, with the same requests. Rocket.Chat's recordings differ run to run (the web client calls `users.info` and `users.presence` at different times), so the IDs differ: the leak and the 10 and 15 by-design lists were the same on both engines; the low member reads and route counts followed each recording. A second run on the same Mattermost recording sent the same requests on each engine.
- The real CLI, end to end on Rocket.Chat 6.13.1 (Docker, a fresh app and recording; `siegekit scan --only access-control --har ... --har-user alice --openapi messaging.yaml`, `test accounts` typed through a pseudo-terminal): 65 requests replayed (26 recorded, 39 swept; 2 routes dropped for no ID, 1 for an address parameter), 9 findings: the leak for both rooms (high and medium), the recording's 3 medium and 2 low, 2 low member reads; `report.json`'s input and result name the sweep and these counts. Run again a minute later on the same app and recording (with the plan line of item 1, added after the first run): the plan names the sweep, 2 answers were 429, `dm.history` was not compared, 8 findings, and the result says coverage may be incomplete.
- Before the fixes, on the same apps: with only the session headers every Rocket.Chat swept route answered A with 401 and the leak was not found (41 swept routes, 148 requests); the address example made Rocket.Chat 6.13.1 fetch `www.w3schools.com` (in `chat.getURLPreview`; sent once, in the first measurement); Gitea sent 1,026 swept routes, 877 answering 404; two Mattermost runs differed by 2 findings (`can_dm`, from the random order of harvested IDs).

After these runs, two spec shapes were found to lose routes silently: a YAML merge key (the route or parameter written through it was dropped) and an unresolved `$ref` (the parameter was dropped and the route sent without it). Both were fixed as described in item 2, and an undeclared `{name}` in a path was counted the same way. None of the 14 measured specs uses a merge key or a `$ref` outside its own document (counted with grep over the YAML files and a walk of Gitea's JSON: no `<<:`, and every `$ref` starts with `#`, 1,501 of them in Gitea's spec). Rebuilding the request lists of all 8 measured runs offline from their saved recordings, before and after the change, differs only in Mattermost's `/api/v4/posts/scheduled/team/{team_id}` (the spec declares no `team_id` parameter), which was sent with the literal braces and answered 404 to alice on both engines, so no finding changes. The apps were not run again for this.

## Consequences

- With a spec, the outsider test reaches routes no client calls. Without one, nothing changes: Rocket.Chat and Mattermost publish theirs outside the app, so the person must fetch them.
- **More false alarms.** Every swept route that answers each logged-in account the same is reported, as recorded requests are (ADR 0035): Rocket.Chat's user, channel, setting and permission lists, Mattermost's team and member profiles for a C who is on the same team. Measured: Rocket.Chat 6.13.1 10 (2 high), 8.9.1 15 (2 high), Mattermost 20 (2 high), Gitea 1 (medium), against 2 real findings on each Rocket.Chat version. People must read them; the reports say each medium may be an answer every account gets. The tiers are not changed here (see Alternatives).
- **Not covered:** `--openapi` takes one file (Rocket.Chat publishes 12: run once per file); IDs the recording did not hold (no guessing, a separate item); parameters named by a slug (`{owner}`, `{repo}`); APIs that refuse the browser session (Gitea's API answers A's cookie with "token is required" on its user routes, so they are not tested from a browser recording); optional parameters; writes; live streams and socket methods; routes in server code but not in the spec (pull request 3).
- The project has its first Go library, vendored; CI builds from `vendor/` with no download.

## Alternatives considered

- **Add `X-User-Id` to the session header list.** Fixes Rocket.Chat only; the next app with a second identity header would fail the same way. Carrying every header of A's request fixes the class.
- **High for a swept route filled with A's ID** (so Rocket.Chat 6.13.1's DM leak, whose 34-character room ID no ID rule knows, would be high rather than medium). Measured on Mattermost's full spec: high findings went from 2 to 14, all by design (team members' profiles, images, statuses). Built, measured and reverted: fewer false highs win, and the leak is still reported, at medium, with "check it by hand".
- **Any of A's IDs for every path parameter.** Gitea: 1,139 requests, 877 swept routes answering 404, the same findings as 201 requests with item 4's rule.
- **`MaxSweep` 300** (first guess): Mattermost's full spec would lose 71 of 371 routes. 1,000: no measured spec needs it.
- **One run with every Rocket.Chat file.** Not built: `--openapi` takes one file today; merging specs is a separate change.
